## “我又发了一条消息，为什么没有新开任务？”

任务（包括 Goal 正在执行的这一轮）还在运行时，新消息会补充到这一轮，而不是开始新任务；如果
恰好赶上这一轮结束或 Goal 换轮，本条消息不会执行，并提示你重新发送。会话正在启动、停止、
收尾或压缩时，普通消息会被拒绝。要开始独立的新任务，请等会话回到空闲、先 `/stop`，或用
`/new`、`/resume` 切换到另一个会话。

详见[一轮任务与补充消息](concepts.md#一轮任务与补充消息)。

## “群里机器人为什么没响应？”

群主线和群话题中的每条消息都必须重新 `@机器人` 才会触发；没有 @ 的消息不会触发响应。若当前
会话选择了“自动带上期间的群聊讨论”，这些消息可能在下一次 @ 时作为背景交给 Codex，但它们
本身仍不会触发任务。还应确认机器人仍在群内，且飞书应用的可用范围和消息权限已经发布。

详见[快速开始](user-guide.md#快速开始)与[群聊消息范围](messages.md#群聊的--时读取的消息范围)。

## “为什么不能修改配置？”

当前会话可能正在运行、停止或压缩。等它回到空闲后再使用 `/config`；要配置另一个会话，先 `/resume` 切换过去。

详见[会话设置](sessions.md#session-settings)。

## “为什么没有执行中表情闪烁或进度卡？”

新建会话默认开启过程卡（Progress Card），默认关闭执行中表情闪烁（Reaction Pulse）；已有会话
保留原来的设置。可以在 `/new` 卡片中选择，或等当前会话空闲后用 `/config` 修改，两项互不依赖。
即使关闭表情闪烁，任务开始、补充消息成功加入和任务结束时仍会尽量显示对应的表情。关闭过程卡
不影响普通任务的最终回复：没有文件时仍回复文本，有文件时仍使用完成卡。Goal 的任务回复也遵循
这项设置，`/goal` 的管理卡单独展示。Side 沿用创建那一刻来源会话的设置；想改变已有 Side 的
反馈方式，需要回到来源会话修改后重新创建 Side。

详见[运行反馈](feedback-and-files.md#飞书中的运行反馈)与[Side 设置](fork-side-goal.md#side-临时话题)。

## “为什么 `/delete` 删除不了？”

已有 Codex 历史的会话，必须是已保存到 Codex 的普通会话，并且当前版本支持删除。任务正在运行、
Goal 运行中、正在压缩，或状态暂时无法确认时，删除也会直接交给 Codex 处理，不需要先等任务结束。
临时会话、未保存的会话、当前版本不支持删除，或 Codex 与存储发生故障时，删除会被拒绝。

- 如果提示中给出了明确的拒绝原因，先处理该原因，再发送 `/delete` 并再次确认。
- 如果提示结果未知，目标会话会保持占用，不要连续点击，应请部署者核查。
- 某个持久分支仍引用来源会话的历史时，也可能无法删除来源会话，需要先处理该分支。
- 请求结果未知或 Codex 中已不存在时，本地关联可能会留下，不会被自动清除；其他会话仍可正常使用。

只想隐藏会话并保留历史时，请使用 `/archive`。

详见[归档、恢复和删除](sessions.md#归档恢复和删除)。

## “Turn 失败后还要换会话吗？”

不用。失败（`failed`）只结束这一轮任务，会话和历史都会保留；回复中会显示可用的错误原因和错误码。
你可以修正问题、调整配置，或稍后发送“继续”，在同一会话开始新一轮。机器人不会自动重跑旧任务，
也不会撤销已经执行过的操作。

如果显示 `turn-observation-unavailable`，说明暂时无法确认这一轮的状态：自动跟进、表情闪烁和
过程卡更新都已停止，原消息上的处理中表情（`Typing`/`THINKING`）也会尽量清理，但这并不表示任务已经结束；之后若
确认任务结束，仍会收到正常的完成回复。

- 这时发送新消息，会先做一次快速检查：确认上一轮已结束，才开始新一轮；上一轮仍在运行，就把本条
  消息补充给它；仍无法确认时，本条消息不会执行，并返回最近的具体原因。
- 也可以在 `/sessions` 中重新检查；确认上一轮失败后，会补发失败原因并解除占用。
- 检查期间若你又停止或切换了会话，等待中的旧消息不会再执行，需要重新发送。
- 如果之前的停止还没完成，检查不会撤销停止；请等待它结束，或按提示重试 `/stop`。停止确认后，
  可以正常发送新消息开始下一轮。旧的过程卡不会恢复更新，新一轮使用正常的反馈。

检查不会重新执行任务。停止、归档或删除仍可从 `/sessions` 操作；归档和删除不需要先恢复状态，
其他会话也不受影响。

详见[一轮任务与补充消息](concepts.md#一轮任务与补充消息)与[会话管理](sessions.md)。

## “换了模型提供方后，旧会话为什么不能继续？”

每个会话会记住创建时使用的模型提供方。服务所在机器的 Codex 配置改用其他提供方后（例如从
OpenAI 换成 Amazon Bedrock 或 Vertex AI），Codex 会拒绝在旧会话里继续执行，回复会写明会话原来的
提供方和当前配置。这条消息不会执行，也不会发给模型；其他会话照常可用，不需要重启服务。

- 想继续旧会话：把 Codex 配置切回原来的提供方，再重新发送。
- 想用新的提供方：发送 `/new` 新建会话。

## “`/stop` 已完成，为什么进程还在？”

`/stop` 能确认这一轮任务已经中断，并请求 Codex 清理它登记过的后台终端，但无法证明前台工具进程
已经退出。这是当前 Codex 接口的限制。

详见[停止任务](status-and-control.md#stop)。

## “CLI 能找到一个工具，为什么飞书里提示找不到？”

先确认工具路径或环境变量已经写入服务账号的持久 shell profile，而不是只在当前终端里临时
`export`。服务每次启动时都会重新读取 interactive login shell 导出的环境；修改 profile 后，需要
部署者执行 `netizen restart --root "<NETIZEN_ROOT>"` 重启对应实例。
alias、未导出的 shell function 和依赖真实终端的初始化，后台服务都无法继承。Bash 用户如果只在
`.bashrc` 中配置了 NVM，需要确认 `.bash_profile` 或 `.profile` 会 source 它。

详见[宿主环境差异](native-capabilities.md#与-codex-appcli-的差异)与[服务与诊断](admin.md#admin-系统维护)。

## “Side 为什么不能继续了？”

Side 会在空闲两小时、服务重启或被关闭后过期。旧的 Side 话题不会变成普通会话；请回到来源会话重新发送 `/side`。

详见[Side 生命周期](fork-side-goal.md#side-临时话题)。

## “引用或图片失败后会不会只发送文字部分？”

不会。引用和图片按整条消息处理：任何一项必需的内容准备失败，整条消息都不会提交给 Codex。
修复权限、缩小图片或重新选择内容后，请重新发送。

详见[消息、引用与图片](messages.md)。

## “为什么任务生成了文件，却没有出现‘本轮文件’？”

本轮文件只来自 Codex 留下的执行记录：成功的文件修改、生成的图片、可用的本轮改动（diff），以及
能确认属于本轮的新建子任务记录。Goal 只取最后一轮，Side 不读取汇总的改动记录，两者都不合并更早
的轮次。子任务记录只读取有限的范围，正在运行或读取不到的文件不保证补齐。机器人不会从最终回复中
解析路径，也不会扫描 Project 目录。因此 shell、MCP 或第三方工具生成、但没有进入这些记录的文件，
以及压缩输出，都不会出现在卡片中。文件还必须仍然存在且是普通文件。Project 不是额外的文件权限
边界，本轮明确记录的其他目录中的文件也可能出现。

详见[本轮文件的来源与展示](feedback-and-files.md#查看和发送本轮文件)。

## “点击本轮文件后，拿到的是任务完成时的版本吗？”

不一定。本轮文件不保存快照、摘要或修改记录；点击时发送的是卡片记录的路径当前的内容。如果其他
会话已经修改、替换或重新指向了这个文件，发送的就是当前版本；如果文件已经不存在或不再是普通
文件，则拒绝发送并保留原卡片。

详见[本轮文件的发送规则](feedback-and-files.md#查看和发送本轮文件)。
