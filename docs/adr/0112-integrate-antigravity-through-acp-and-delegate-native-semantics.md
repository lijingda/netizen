# 通过 ACP 接入 Antigravity，并把原生已实现的语义交给原生决定

## 背景

[ADR 0111](0111-define-an-extensible-backend-contract.md) 定义了后端契约。维护者随后按这份契约评估 Google Antigravity 作为下一个后端。评估分三步：官方资料与无认证握手；两种接入面的源码比较；用维护者自己的登录，分别在 1.5.12 和 1.5.18 上实测。调研记录保存在本地研究目录 `docs/research/antigravity/`。

Antigravity 有两种程序接口：

- `agy acp`：用户本机的 `agy` 以子进程方式提供 ACP（Agent Client Protocol）v1 的 JSON-RPC 服务。协议组织发布了官方 Python 客户端库 `agent-client-protocol`，许可证为 Apache-2.0，类型由官方 schema 生成，可以精确固定版本。
- Python SDK `google-antigravity`：启动 SDK 自带的运行时，和用户在 CLI 里的会话不互通。它不报告实际 cwd，每条输入没有可配对的标识，停止请求不带执行标识，忙时发送会等待上一轮结束。

在 `agy acp` 1.5.18 上实测到：

- 第一条输入之前就有会话 ID，可以列出会话，也可以跨进程按 ID 续接；
- 续接时即使传入别的目录，会话仍在原 cwd 中执行，会话列表也报告原 cwd；
- 一次请求对应一个应答，应答带 `stopReason`；
- 忙时再发一条请求，前一条请求立即返回，后续工作由后一条承接；
- 非 daemon 的后台工作在应答之前完成；
- 模型选择 daemon 方式时，后台输出会出现在应答之后，只带会话 ID；
- 运行中的取消由目标请求的 `cancelled` 应答确认，取消通知本身没有回执；
- 进程被强制结束后，原请求的终态无法找回；
- 工具调用带 diff；
- MCP 工具调用的 `_meta` 带 agy 附加的会话 ID。

维护者的判断是：Netizen 是驱动用户自有 Agent 的 Channel，不是另一个 Agent，Antigravity 官方 ACP 文档也说明任何 ACP 客户端都可以启动它。Google 的消费者条款限制第三方软件包装 `agy`，这项风险由维护者承担，接入范围先限于所有者本人。

## 决定

### 1. 通过 `agy acp` 和官方 ACP 客户端库接入

- Netizen 作为 ACP 客户端，驱动用户自己的 `agy` 运行时。会话、配置和权限都属于这个运行时。
- 客户端只使用精确固定版本的 `agent-client-protocol`，不手写协议模型。
- 不采用 Python SDK，原因见背景。

### 2. 原生已实现的语义交给原生决定（修订 ADR 0111）

这是一条适用于所有后端的通用规则：

- **宿主只核验宿主自己的状态**：Scope 和 Binding 的身份、准入版本、群聊游标、所有者门禁、Project 与 Worktree 状态，以及模块能力项是否开放。
- **原生自己的语义交给原生**：忙时如何处理、配置值是否合法、权限策略、会话状态是否允许某个操作。Netizen 直接发出请求，按原生应答映射结果，不重复做判断。
- **判断标准**：原生的应答能不能证明发生了什么。
  - 能证明，就委托。
  - 委托会产生无法归属或无法撤销的效果时，宿主才前置拒绝。例如 Codex 的压缩应答不带轮次标识，压缩期间宿主拒绝新输入。

Codex 现有的前置检查不单独排查，在 ADR 0111 第 6 条的核心边界整理中按这条规则逐项对照。

### 3. 忙时输入的第二种方式（修订 ADR 0111 第 2 条）

核心契约允许两种忙时处理方式：

- **宿主在写入前拒绝**：适用于原生不能对忙时请求逐条给出明确应答的后端。
- **由原生逐条应答**：原生对每条请求都给出明确的接受、拒绝或终态时，宿主不做忙时前置判断。

运行中追加输入也分成两种模型：

- **并入**：后一条输入并入正在执行的那一轮，两者共用一个终态和投递锚点。Codex 属于这种，对应“运行中追加”模块。
- **接续**：后一条请求接手执行，前一条请求随即结束，每条请求各有自己的终态。Antigravity 属于这种。它是核心契约允许的“由原生逐条应答”，不需要声明“运行中追加”模块。

### 4. Antigravity 的核心事实映射

| 核心事实 | Antigravity 的满足方式 |
| --- | --- |
| 会话身份与写入目标 | `session/new` 在第一条输入之前返回会话 ID。宿主先在 Binding 上登记该 ID，再发送输入。 |
| 实际工作目录 | 续接前从 `session/list` 中按精确会话 ID 取得 cwd，再用这个值续接。 |
| 执行身份 | 同一条连接上，JSON-RPC 请求与应答一一配对，再加上第 5 条的归属规则。 |
| 接受判定 | 请求的正常应答是晚到的接受正证。门禁证明发生在执行之前的错误应答，才算“明确未投递”。其他错误和连接中断都是“效果未知”。 |
| 终态与结果 | 终态取应答中的 `stopReason`；正文取该请求窗口内按第 5 条归属的消息片段。 |
| 重检 | 原生没有按请求重取终态的接口，重检始终得到“仍未知”，按既有规则只隔离这个 Binding。 |
| 停止 | 只在目标请求仍未应答时发送 `session/cancel`。停止进行期间，宿主不向这个会话发送新请求。目标请求返回 `cancelled` 即停止生效；它已经先返回时，丢弃这次停止。原生取消会同时结束该会话的后台工作，停止入口要说明这一点。 |
| 观察源 | 每个活动会话一条连接，由一个客户端读取，其他模块复用它的投影。 |
| 发行物与停服 | 启动时核实 `agy` 的版本属于已验收的范围，并核实 `initialize` 报告的 agent 版本。服务启动的 `agy` 进程关闭自动更新。停服在截止时间内关闭各条连接和进程。 |

### 5. 输出归属与降级

- 有请求未应答时，会话输出归属最近发出的那条请求。
- 没有未应答的请求时出现的输出，走“会话输出”降级路径：以普通文本发到这个 Binding 所在的位置，不改变任何输入的状态，也不产生 Files。
- Netizen 不解析具体工具的参数，例如是否以 daemon 方式运行。
- **停止的交界竞争**：取消已发出，目标请求却以 `end_turn` 等正常原因返回时，取消的效果无法确定。此时走通用降级：回收这个会话的连接，下一条输入在新连接上续接。为此每个活动会话使用独立的连接和进程，回收只影响这个会话。
- 连接的保留与释放沿用现有的会话订阅规则。关闭连接可能结束原生后台工作，释放入口要说明这一点。

### 6. 范围与顺序

- Antigravity 实例只供所有者本人使用：实例只有一名管理员，只有所有者能触发执行或修改将要执行的内容，Admin 不能添加管理员。
- 按以下顺序推进，每一步单独提交和验收：
  1. 按 ADR 0111 第 6 条整理核心边界，只修改 Codex，做行为冻结，并按本 ADR 第 2 条对照 Codex 的前置检查。
  2. Antigravity 核心普通会话：版本门禁、进程模型、归属规则、降级路径和所有者门禁。
  3. 按顺序逐个开放模块：会话目录（`session/list`）、Activity（工具调用与计划的安全投影）、本轮文件（请求窗口内的工具 diff）、阶段性答案（请求窗口内的消息片段）、模型设置（会话配置项）、图片输入。每个模块补全卡片，带契约断言和原生门禁。
- 协作、提问、定时派发等其他模块以后另行决定。

### 7. 已知限制

- 两条请求重叠的几毫秒内到达的少量输出，可能归到相邻的请求。
- daemon 方式的后台工作如果在下一条请求的窗口内输出，会算作那条请求的内容。
- 进程被强制结束时，正在执行的请求的结果保持未知。
- 升级 `agy` 后需要重新验收，验收前服务拒绝启动。

## 备选方案

| 方案 | 取舍理由 |
| --- | --- |
| 通过 `google-antigravity` SDK 接入 | 它自带运行时，和用户的 CLI 会话不互通，也缺少实际 cwd、逐输入标识和带目标的停止。 |
| 宿主在忙时前置拒绝 Antigravity 的输入 | 原生已经对忙时请求逐条应答，宿主再判断一次，既重复了原生语义，也丢掉了原生的接续能力。 |
| 解析 daemon 等工具参数来判断会话是否忙 | 这些参数属于具体工具，不在协议之内，换个版本就可能改变。 |
| 停止后等待固定时长，再允许新请求 | 等待时长不是原生事实，ADR 0111 不允许用时序作为证明。 |
| 用自写的 JSON-RPC 客户端 | 需要复制协议模型，而官方库已经存在。 |

## 后果

- 委托原生语义成为通用的设计原则。AGENTS.md 和贡献指南各加一条；工程设计的后端契约补上忙时处理的两种方式和两种 steer 模型。
- Antigravity 的具体行为在每一步实现时写入工程设计；在此之前，当前契约中的后端仍只有 Codex。
- 每次升级 `agy` 或 `agent-client-protocol`，都要重新验收第 4 条和第 5 条依赖的原生事实。
