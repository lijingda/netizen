# 用飞书过程消息作为展示 Turn 的第二种形态

## 背景

[ADR 0106](0106-present-each-physical-turn-as-one-feishu-presentation-turn.md) 把每个物理 Turn 映射为一个飞书展示 Turn，具体展示形态沿用现有的传输规则。

- 开启过程卡时，回复是一张卡，包含 Activity、阶段性答案、Result 和 Files。
- 关闭过程卡时没有 Activity。阶段性答案和无文件的结果用富文本发送；有文件时，发一张 Result+Files 卡。

维护者要求两种形态都带过程信息，只在呈现方式上区分：一种是卡片，另一种是过程消息加普通消息。这样，后续 Claude 的 Activity（[ADR 0105](0105-extend-backends-through-capabilities-and-shared-presentation.md) D①）只需投影一次。

以下事实的来源有三部分：

- API Explorer 的接口定义；
- 固定 SDK 和 `lark-oapi` 1.8.0 的源码检查；
- 多轮实机验证：用试点应用在一个指定测试群中进行，接口请求和回执见记录；显示效果来自维护者随后对桌面端和移动端的核对反馈。

这些材料保存在本地研究目录 `docs/research/multi-agent-positioning/phase5/` 下的 `COT-FACTS.md` 和 `COT-LIVE.md` 中。

- **接口。** 飞书提供独立的 IM 资源 `message_cot`，有三个接口：
  - 创建：可以指定 `origin_message_id` 和 `reply_in_thread`，返回值只有 `cot_id` 和 `message_id`；
  - 更新：提交一个 AG-UI 事件列表；
  - 完成：原因为 `done`、`error` 或 `timeout`，完成后不可逆。

  Explorer 列出的调试权限是 `im:message` 和 `im:message:send_as_bot`，Netizen 已经申请了这两项。频率档位为每个接口、每个应用、每个租户每秒 50 次，每分钟 1,000 次。
- **文档与 SDK。** 已检查的公开消息开发文档索引、本机 lark skill 和 lark-cli 1.0.99 都没有涉及这个资源。固定的 `lark-channel-sdk` 1.4.0 没有它；`lark-oapi` 1.7.2 和 1.8.0 只带事件模型，没有可以调用的接口。
- **实机记录（与文档示例有出入）。**
  - 文档示例中的 `toolcall` 会被拒绝。已接受的事件类型有 `STEP_STARTED`、`TOOL_CALL_START`、`TEXT_MESSAGE_START` 和 `ACTIVITY_SNAPSHOT`，时间戳为 10 位秒。这并不代表完整词表，也不代表唯一可用的单位。
  - API 接受按同一身份重发的事件。不同客户端对重发、替换和配对的显示有差异。
  - 在桌面端验证的配对写法将开始与结束事件放入同一次更新，使已完成条目显示对勾。
  - 桌面端 P10 的 `ACTIVITY_SNAPSHOT` 只显示 v2。手机端 E1–E5 均显示 v1 和 v2，包括按 P10 原样重做的 E1。两台手机对 P8、P9 的显示也有差异。
  - 完成后再更新，返回 10001。
  - 重叠的更新可能返回 10020（请求正在处理）。
  - 用填充过的 `STEP_STARTED` 测试单事件大小：2,000 字可以，10,000 字被拒绝。
  - `done`、`error`、`timeout` 分别显示为"任务已完成""任务失败""任务超时"。
  - `cot_hidden` 会让消息完全不可见。
  - 在已有话题中，过程消息和最终消息位于同一话题，并以原消息为直接父消息。

  维护者决定本版采用原生过程消息，以逐项 START/END 表达完成，接受当前客户端的显示差异。客户端的最低版本和旧版本上的具体显示未经验证。

## 决定

### 1. 两个相互独立的设置维度

- **回复消息类型。** 可选"卡片"或"过程消息"，按 Binding 保存，沿用现有的布尔值：开表示卡片，关表示过程消息。
  - 实例兜底不提供这一项，只有显式值。
  - 所有历史显式值保留原值，按新的映射解释。
  - 不新增数据库结构。
- **展示细节。** 即 [ADR 0086](0086-configure-progress-card-presentation-with-bounded-activity-segments.md) 中的八项设置，同样适用于两种类型。缺省时仍按 [ADR 0087](0087-use-instance-progress-card-settings-for-missing-session-intent.md) 在捕获执行设置时读取实例兜底，捕获时机是普通 Turn 准入、新的 Goal 运行开始或 Side 创建。保存无关修改时，保留空值和与默认值相同的显式值。

展示细节仍在现有的 Admin 细节编辑器中编辑，两种类型下都可见、可编辑，并标明来源。`/status` 显示所选的回复类型。现有的飞书表单保留类型选择，往返时保留空值。

过程信息暂时始终显示，以后按需决定是否增加开关。

Codex 普通 Turn、Goal 和 Side 与 Claude 都采用这一规则。Side 的每一轮回复使用创建 Side 时冻结的 Parent 选择；Side 话题的根卡和会话容器不变（修订 [ADR 0048](0048-integrate-side-turns-with-task-feedback-reply-cards.md)）。

### 2. Activity 的观察不再依赖传输选择

普通 Turn、Goal 和 Side 都通过现有的观察链或 Tap 取得 Activity，与回复类型无关。既有约束全部不变，包括单一消费者、安全允许清单、Side 的 high-water 降级，以及阶段性答案和问题的独立投递（修订 [ADR 0052](0052-project-safe-turn-activity-with-one-consumer.md) 中按开关决定是否观察 Activity 的条款）。过程消息只投影 Activity 字段。

### 3. 承载内容的操作保持不变

两种类型中，承载答案内容的操作如下：

- **卡片：** 维持现状，包括原卡上的终态更新、该路径的回执，以及以卡片为锚点的结束提及。
- **过程消息：**
  - 每个完整的阶段性答案，仍按现有规则立即作为带标签的富文本发送；
  - 无文件的最终结果用富文本发送；
  - 有文件时，发一张现有的 Result+Files 卡。
  - 最终普通消息保留发送时的后台任务数后缀和 `/release` 提示。

答案的投递账本、单次未送达提示、[ADR 0063](0063-mention-task-initiators-in-terminal-results.md) 的提醒和例外，以及定时首轮回执，都只认这些普通消息。问题卡按各自的物理 Turn 和条目独立投递；Files 卡的回调自带清单。这两者仍按现有规则处理，不依赖答案消息。

过程消息的创建、更新和完成都不承载内容，不能证明答案已送达，也不能作为提醒锚点。

### 4. 过程消息逐项追加活动，完成时配对结束事件

每个展示 Turn 最多对应一条过程消息。工具操作、进行中的清单步骤和已完成的进展文字来自与卡片相同的安全 Activity 投影。
条目的稳定身份由展示 Turn 和原生 Activity 身份共同确定。首次写入时固定文字，之后只补充结束事件。过程消息不显示状态行。

| 条目 | 事件与安全字段 |
| --- | --- |
| 工具操作 | 运行时发送 `TOOL_CALL_START`（`toolCallId`、投影中已过滤的操作标签 `toolCallName`）。完成后同时发送原 START 和同一 `toolCallId` 的 `TOOL_CALL_END`。 |
| 清单步骤 | pending 步骤不展示。进行中发送 `STEP_STARTED`，完成后同时发送原 START 和 `STEP_FINISHED`。配对使用同一份固定的 `stepName`。 |
| 已完成的进展文字 | 一次发送 `TEXT_MESSAGE_START`（`messageId`、`role=assistant`）、`TEXT_MESSAGE_CONTENT`（相同 `messageId` 和安全文字 `delta`）、`TEXT_MESSAGE_END`（相同 `messageId`）。 |

每次写入发送当前完整的条目列表，每个 END 都带上其 START。过程消息靠原生配对表达完成勾选。
不发送 `TOOL_CALL_ARGS`、`TOOL_CALL_RESULT` 或 `REASONING_*`，不包含推理内容、原始工具参数或原始输出。

- **写入。** 按当前状态计算期望列表，与已知列表不同时才写入。结果未知时，下次触发重写。每条消息只有一个写入者，中间状态不排队，失败只影响本次写入。
- **时间。** 各事件使用 10 位秒时间戳。START 取首次观察时间，END 取观察到完成的时间，最早为 START 所在秒。进展文字在观察到完成时即可同秒发送三个事件。重发沿用原时间。列表按时间排序，同秒按稳定条目身份排序，条目内保持 START、CONTENT、END 的顺序。
- **预算。** 每项可见文字最多 300 个 Unicode 字符，截短时保留省略号。每个事件的完整内层 JSON（含字段、身份和转义）最多 1,800 个 Unicode 字符。
- **60 项滑动窗口。** 每次写入优先保留运行中条目，以便之后在同一份列表中发送其 START 和 END。如果运行中条目超过 60 项，保留最早开始的 60 项，同秒按稳定条目身份排序。较晚开始的条目在出现空位时依次纳入。其余空位保留最近完成的条目，最早完成的条目先移出。只渲染最新列表的客户端看到窗口向前滚动，合并历次列表的客户端仍可能显示已移出的条目。维护者接受这种差异。
- **收尾。** 完成过程消息前，将当前列表中仍在运行的条目全部补齐 END，做一次有界最终写入，再按第 5 条完成一次。

### 5. 生命周期

- **创建：**
  - 展示 Turn 在确实有可见内容时才创建过程消息。
  - 匿名唤醒和 cron 的 Turn 在 Result 时才确定是否创建：既没有正文、也没有阶段性答案的匿名成功结果不创建，不论有没有 Activity。
  - 位置与该路线的普通回复一致：有人工来源时回复原消息；无人工归属时，发到已核实的会话位置。
- **位置校验：** 该路线要求明确确认位置时（话题、定时首轮、无归属的话题结果），创建后对返回的消息做一次有界的精确读取，核对聊天、根消息、话题，以及直接父消息是否为该路线实际的父消息。有人工来源时，父消息是 Completion Origin；定时首轮的父消息是已发布的根或种子消息；无归属的 Claude cron 话题结果，父消息是已核实的 Binding 话题根。核对矛盾时，按现有的 Binding 级停用规则处理。无法确认时，不再写入这条过程消息。无论哪种情况，答案都照常投递。返回的 ID 对只由一个展示 Turn 独占。创建回执丢失或格式错误时，不再重复创建。
- **完成：**
  - 以下三种情况任一发生，就完成该展示 Turn 的过程消息：它不再是该输入最新的已确认过程消息；它所属的运行结束；运行时以类型化事件给出该 Turn 执行结果未知（这是独立的触发条件，原因为 `timeout`）。
  - 结果未知之后，同一 Turn 如果恢复并确认了结果，只照常投递普通消息，不重开、不新建过程消息，也不伪造原生终态。
  - 无人工归属的 Turn 在它自己的物理结果到达时完成。
  - 完成前按第 4 条补齐运行中条目的 END 并限时写入最终列表。即使最终列表写入失败，仍请求完成一次，随后收回写权。
- **完成原因：** 由展示 Turn 自身的类型化终态决定。

  | 终态 | 原因 | 显示 |
  | --- | --- | --- |
  | 完成 | `done` | 任务已完成 |
  | 用户中断 | `done` | 任务已完成，后续普通消息照常说明已中断 |
  | 失败 | `error` | 任务失败 |
  | 执行结果未知 | `timeout` | 任务超时 |

- **执行结果未知：** 由运行时以类型化事件给出，并照常发出已有的通知。
- **观察中断：** 只有 Activity 观察中断时，停止刷新不可用的 Activity 字段，已知条目仍由同一写入者持有，不提前完成。之后若确认了最终结果，补齐 END 并按实际终态完成。

### 6. 用窄适配层调用三个接口

在官方 SDK 提供 `message_cot` 之前，新增一个窄适配层，参照 [ADR 0014](0014-use-removable-sdk-gap-adapters.md) 和 [ADR 0080](0080-authenticate-admins-with-feishu-identities.md) 的先例。

- **范围：** 只暴露创建、更新、完成三个类型化操作。通过固定 `lark-oapi` 的公开请求接口发出，使用同一应用凭据，并与 Channel SDK 处于同一个实例生命周期。
- **限制：** 不提供通用调用入口，不解析非公开字段，只读取 `cot_id`、`message_id` 和错误码。历史读取端口保持只读。
- **移除条件：** `lark-channel-sdk` 或 `lark-oapi` 提供类型化的 `message_cot` 接口后，在相同的行为门禁和实机门禁下改用官方接口，再删除本适配层。
- **门禁：** 包括请求与响应的形状测试、使用已安装客户端的合成失败与并发测试，以及按需运行的实机验证。实机门禁只核对创建、更新和完成的 API 回执，完成后更新被拒绝（10001），精确聊天、话题、根及直接父消息位置，以及单事件 1,800 字符预算获接受。重叠写入样本允许 0 或 10020，是否出现 10020 只供记录。触发条件见 `docs/deployment.md`。维护者在桌面端单独记录显示观察。
- **门禁失败时：** 实机门禁不通过时，过程消息类型降级为只发送第 3 条中的普通消息，答案不受影响。

### 7. Codex 卡片投递与 ADR 0106 的 Goal 步骤

- **Codex 卡片投递：** 本决定不改变 Codex 的卡片投递。维护者已于 2026-11-24 同意把 Codex 卡片迁入单消息对账，届时另写 ADR，逐项列出失败路径上的变化。
- **Goal 按物理 Turn 展示：** [ADR 0106](0106-present-each-physical-turn-as-one-feishu-presentation-turn.md) 的这一步暂缓，PR #323 已经停放。恢复前须完成两项：
  - 投递统一；
  - 每个已结算的 Turn 只从精确的原生历史读取内容，以替换 ADR 0106 第 6 条中基于 Tap 冻结事实的做法。

  在此之前，Goal 保持兼容映射：一个逻辑运行只对应一个展示 Turn；过程消息类型下，最多一条过程消息，换轮时沿用同一条过程消息，新物理 Turn 的 Activity 使用可区分的条目身份。

## 实施与验收

1. 先实现第 6 条的适配层及其门禁。
2. 再实现回复类型、Activity 观察和过程消息形态，Codex 和 Claude 都经由 #317 的通用展示层。
3. 冻结对照：
   - 卡片类型的全部输出保持不变；
   - 过程消息类型与原先"关闭过程卡"的输出相比，对外写入只允许多出过程消息的创建、更新和完成，另外允许路线要求时的那次有界位置读取；其余承载内容的操作保持不变；
   - 这一例外对 Codex 普通 Turn、Goal 和 Side 同样适用。
4. 时序探索测试覆盖以下情况：
   - 创建、更新、完成；
   - 结果未知、写入失败、并发拒绝；
   - 被新一轮取代时成对写入仍在运行条目的结束事件；
   - 运行结束时的收尾；
   - 大小预算；
   - 按时间排序、同秒配对顺序及重发时间稳定。
5. 在指定测试会话中核对过程消息的 API 回执，由维护者单独记录桌面端的显示。

阻断标准沿用 ADR 0106，但第 3 项允许的例外除外。以下情况同样阻断：

- 过程消息中出现推理内容、原始参数或原始输出；
- 把过程消息当作答案已送达的证据或提醒锚点；
- 完成后仍有写入；
- 同一条过程消息有并发写入；
- 过程消息写到了未经确认的位置。

## 备选方案

| 方案 | 结论 |
| --- | --- |
| 使用单个可替换快照 | 相同事件在桌面与移动端的替换结果有差异，逐项开始与结束可以直接表达每项的完成。 |
| 等官方 SDK 支持后再做 | 不采用。支持时间不确定，维护者希望先统一形态。 |
| 只给 Claude 提供过程消息 | 不采用。两个后端在展示层上应保持一致。 |
| 把阶段性答案放进过程消息 | 不采用。客户端可能折叠或隐藏过程，用户会错过答案，投递回执也无从区分。 |
