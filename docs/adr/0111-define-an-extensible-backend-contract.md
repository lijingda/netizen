# 以核心契约和能力模块定义可扩展的后端契约

## 背景

[ADR 0104](0104-host-native-agent-backends-per-instance.md) 让每个实例固定一个原生 Agent 后端，[ADR 0105](0105-extend-backends-through-capabilities-and-shared-presentation.md) 引入了静态工厂、按调用方的小接口、操作描述、共用展示模型和四项执行不变量。Claude Code 试点按这套机制接入，随后由 [ADR 0110](0110-withdraw-the-claude-code-backend.md) 撤回。试点暴露了三个问题。

- **契约没有成文。** Netizen 的保证（准确的执行身份、受理后才推进游标、终态或明确的未知、只停当前执行）隐含在 Codex 运行时里。另一个后端能否满足，只能靠抓包和多轮复审逐项发现。
- **差异流进了共用层。** 普通会话之外的通用能力（会话目录、归档、恢复、设置、定时、协作）没有接口。试点只能在管理和 Channel 中另开 `local` 平行路径，共用展示器也加入了只属于该后端的投递模式。撤回时这些分支散布在三十多个共用文件中。
- **证明依赖实测时序。** 缺少原生事实的地方，用固定版本下测得的顺序和等待时长来推断。每次上游升级都要重新证明。

在 `main@78b8f5b`，Channel、管理、定时、协作和 Worktree 五层仍有约 124 处直接调用 `CodexRuntime`，涉及约 66 个方法。维护者还要求契约可以扩展：以后接入的 Agent 可能带来新的特性，这些特性可以定义成 Netizen 的通用能力，Codex 也能按同一契约实现，从而增强 Netizen 在 Codex 上的能力。

## 决定

### 1. 后端契约分为核心契约和能力模块

- **核心契约**是每个后端都必须满足的普通会话能力：有身份的、按顺序执行的普通会话。
- **能力模块**是其余所有可选能力。每个模块用 Netizen 的语义定义，不照搬任何一家 Agent 的原生形状。后端声明并通过验收的模块才开放，其余模块在所有入口关闭。
- 当前契约、模块表和模块卡片写在 [工程设计的后端契约](../design.md#后端契约)。本 ADR 规定结构、扩展流程和结构规则。

### 2. 核心契约

后端必须由原生直接提供以下事实，不能用推断、时序或本地状态代替：

1. **会话身份**：首次执行之前或之时得到稳定的原生会话 ID，之后可以按该 ID 续接。
2. **实际工作目录**：原生会话的实际 cwd 由原生报告，续接前可以按会话 ID 核实。
3. **接受证明**：能归属到这条输入的原生证据，表明它已进入执行，或已被明确拒绝且未投递。证据可以晚到，最晚与终态同时到达。证据到达前，这条输入的状态是“未定”；连接中断而没有证据时，状态是“未知”。
4. **终态**：每条已接受的输入都有能归属到它的终态（完成、中断、失败），或者明确的未知。超时和静默不能当作终态。
5. **停止**：可以只停止当前执行，旧的停止请求不能命中后继执行。原生停止的作用范围大于当前执行时（例如同时停止后台工作），后端须在契约中写明，并在停止入口说明。
6. **事件流**：Netizen 是该会话原生事件流的唯一消费者。后端把原生事件翻译成共用展示事件，不把原生类型交给共用层。
7. **启动与停服**：启动时核实固定的原生版本；停服时在 Netizen 给出的截止时间内关闭本实例的原生连接，未确认关闭时保留隔离。

运行中追加输入（steer）不属于核心，是一个能力模块。未声明该模块的后端在忙时于写入前拒绝新输入，提示用户稍后重发，不排队。

以下宿主不变量由 Netizen 实现一次，对每个后端都生效，后端只提供上述原生事实：

- 捕获输入后在提交前比较 Binding 版本，A→B→A 切换后旧捕获失效；
- 有接受证明后才推进群聊游标，持久化失败时关闭后续准入并继续交付这次已接受的执行；
- 停止前比较 Binding、版本和执行身份；
- 停服时从总预算中为展示和存储清理预留时间。

### 3. 能力模块与模块卡片

每个模块有一张卡片，字段固定：

| 字段 | 内容 |
| --- | --- |
| 标识与名称 | 稳定的模块标识，以及它对应的操作描述条目 |
| Netizen 语义 | 用户和管理员看到什么、Netizen 保证什么，不提任何一家 Agent |
| 端口 | 宿主调用的最小操作和后端产生的事件，用 Netizen 的术语写 |
| 原生事实 | 兑现语义所需的契约层事实，与某个后端的实现机制分开 |
| 入口与资格 | 命令、卡片、Admin API、定时派发中哪些入口使用它，以及资格条件 |
| 失败与降级 | 唯一的降级路径、影响范围和提示 |
| 展示事件 | 使用共用词汇表中的哪些事件 |
| 验收 | 与后端无关的契约测试，以及每个后端自己的原生门禁 |
| 依赖 | 依赖的其他模块；同组模块不互相授予资格 |
| 实现状态 | 各后端是否实现、经由端口还是仍直连运行时 |

模块卡片在模块首次有第二个实现、首次由新后端提出、或其边界被修改时补全。在此之前，模块表中的一行就是它的当前定义。

### 4. 扩展流程

1. **提出**：任何后端的原生能力，按[保留原生能力](../design.md#目标与边界)和飞书场景的收益权衡后，都可以提出为新模块或对已有模块的扩展。
2. **定义**：写出模块卡片。语义和端口用 Netizen 的术语，不照搬发起方 SDK 的类型或调用顺序；必须写明降级路径和验收方式。新增端口、新增展示事件或改变共用边界时写 ADR；只在已有端口和事件内增加行为时，直接更新工程设计中的模块表和卡片。
3. **注册**：在操作描述中登记对应的操作和提供方。没有装配提供方的后端，在所有入口上用同一套资格判定拒绝，包括手输命令、旧卡回调、Admin API 和定时派发。
4. **实现**：每个后端独立实现端口，通过该模块的契约测试和本后端的原生门禁后开放。Codex 采纳由其他后端提出的模块，同样走这一步。
5. **修订与移除**：模块语义变化时修订卡片，不在共用层按后端区分行为。一个模块不再有任何实现时，从代码中移除；需要时按本流程重新提出。

### 5. 结构规则

1. **能力要么映射到端口，要么关闭。** 共用层（Channel、管理、定时、协作、Admin、展示）不按后端身份分支，不开平行路径。后端身份只出现在装配和显示名称中。
2. **展示事件词汇表封闭。** 共用展示只消费 TurnOpened、ActivityChanged、PartialAnswer、RunState、TurnResult、RunEnded 和 DeliveryReceipt，投递策略只有一种。新增事件或投递模式需要 ADR，并且要有至少一个真实后端的生产者和真实的消费者。
3. **保证只建立在原生公开报告的事实上。** 这些事实由门禁固定。实测时序和等待时长不能作为证明。缺少事实时，关闭对应模块或走它的降级路径。
4. **通用门禁绑定其实际触发事实。** 打包、回执、准入屏障等通用检查不能挂在某个后端专属的键或标志上。
5. **契约测试与后端无关。** 核心和每个模块各有一组契约测试，每个后端用自己的合成实现运行它声明的全部部分。

### 6. 演进方式

- Codex 是参考实现，满足核心契约和多数模块，但很多调用仍直连 `CodexRuntime`。不做一次性重构。
- 当第二个后端要实现某个模块，或 Codex 要采纳一个新模块时，先在 Codex 上把对应调用移到该模块的端口后面。这一步是行为冻结式重构：改动前冻结 Codex 的解码输出，改动后逐项比较。然后再接入新的实现。
- 接入第二个后端之前，必须先整理核心边界：
  - Channel 和管理装配只依赖核心端口；
  - 宿主不变量与 Codex 的证明条件分开；
  - 状态提供方与后端无关；
  - 展示接线由提供方翻译原生事件。

### 7. 暂不纳入

原生输出无法归属到任何已接受的输入时（例如后台工作结束后自行唤醒的回复），本 ADR 不规定其处理方式。实际接入的后端需要时，按扩展流程以新模块定义。

## 备选方案

| 方案 | 取舍理由 |
| --- | --- |
| 一个覆盖所有能力的大接口 | 后端要为缺失能力提供空方法，调用方容易把占位结果当作有效数据。ADR 0105 已否决。 |
| 以 ACP 等现成协议作为 Netizen 的后端契约 | 协议只是某个后端的传输。Codex 不走该协议，Netizen 的 Scope、Binding 和飞书投递语义也不在协议范围内。模块定义可以参考协议，但不以它为准。 |
| 只写原则，不写模块表和卡片 | 原则无法在复审中逐项核对，试点就是在缺少成文条目的情况下逐项发现缺口。 |
| 先抽取完整的执行内核，再接入新后端 | 只有一个实现时抽取的内核会带着这个实现的形状。按模块在真实的第二个实现出现时再移到端口后面。 |
| 把无法归属的原生输出纳入核心 | 目前没有实际接入的后端可以验证规则，按维护者裁定暂缓。 |

## 后果

- 新后端的评估从核心契约的原生事实清单开始。事实不满足时，在写代码之前就能判断它不能接入，或只能接入到哪一层。
- 新能力可以由任何后端首先提出，再由 Codex 等其他后端按同一模块实现。
- 复审有了可以逐项核对的门槛：共用层中的后端分支、共用展示中的新投递模式、依赖时序的证明、挂在后端专属键上的通用检查，都属于阻断问题。
- 接入第二个后端前需要先完成第 6 条列出的核心边界整理。这部分工作随具体后端的接入决定一起排期。
