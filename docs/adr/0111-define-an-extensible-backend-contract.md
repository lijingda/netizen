# 以核心契约和能力模块定义可扩展的后端契约

## 实现进展

2026-11-26，#334 已补齐第 6 节记录的 Codex 停止缺口。启动回执返回前发出的停止请求会等待本次启动结果，仅中断仍在运行的目标 Turn。见[普通 Turn 停止与压缩](../design.md#普通-turn-停止与压缩)和[启动窗口停止测试](../../tests/test_turn_start_stop.py)。

## 背景

[ADR 0104](0104-host-native-agent-backends-per-instance.md) 让每个实例固定一个原生 Agent 后端。[ADR 0105](0105-extend-backends-through-capabilities-and-shared-presentation.md) 引入了静态工厂、按调用方的小接口、操作描述、共用展示模型和四项执行不变量。Claude Code 试点按这套机制接入，随后由 [ADR 0110](0110-withdraw-the-claude-code-backend.md) 撤回。试点暴露了三个问题。

- **保证没有汇总成可验收的契约。** 单写入、准入版本、受理后推进游标、精确停止和停服预算分别记在既有 ADR 和工程设计中，但没有一份清单写明后端必须提供哪些原生事实。另一个后端能否满足，只能靠抓包和多轮复审逐项发现。
- **差异流进了共用层。** 部分通用能力已有读接口，但装配和若干调用仍依赖具体运行时。试点只能在管理和 Channel 中另开 `local` 平行路径，共用展示器也加入了只属于该后端的投递模式。撤回时这些分支散布在三十多个共用文件中。
- **证明依赖实测时序。** 缺少原生事实的地方，用固定版本下测得的顺序和等待时长来推断，每次上游升级都要重新证明。

在 `main@78b8f5b`，Channel、管理、定时、协作和 Worktree 五个目录共有 124 处对 `self._runtime` 的成员访问，涉及 62 个成员名，其中 113 处是直接方法调用，涉及 58 个方法名。部分接收者是管理包装或已有端口。维护者还要求契约可以扩展：以后接入的 Agent 可能带来新的特性，这些特性可以定义成 Netizen 的通用能力，Codex 也能按同一契约实现，从而增强 Netizen 在 Codex 上的能力。

## 决定

### 1. 后端契约分为核心契约和能力模块

- **核心契约**是每个后端都必须满足的普通会话能力：有身份的、按顺序执行的普通会话。
- **能力模块**是其余所有可选能力。每个模块用 Netizen 的语义定义，不照搬任何一家 Agent 的原生形状。模块由可以单独启用的能力项组成。后端声明并通过验收的能力项才开放，其余在所有入口关闭。
- 当前契约、模块表和模块卡片写在[工程设计的后端契约](../design.md#后端契约)。本 ADR 规定结构、扩展流程和结构规则。

### 2. 核心契约

核心契约的宿主语义沿用工程设计中的既有规则，不在本 ADR 中重写：[锁与输入准入](../design.md#锁与输入准入)、[普通 Turn 终态与观测恢复](../design.md#普通-turn-终态与观测恢复)和[失败语义](../design.md#失败语义)。后端必须提供让这些规则成立的事实，不能用推断、时序或本地状态代替：

1. **会话身份与写入目标**：首次执行之前或之时得到稳定的原生会话 ID，可以按该 ID 续接。在输入可能生效之前，宿主在本实例内唯一登记 Binding 到原生写入目标的关系；冲突和不确定的结果按该原生会话的所有权语义处理。
2. **实际工作目录**：续接以原会话 ID 为目标。对已物化的会话，最迟在依赖 cwd 的准备或新输入写入之前，从该会话的原生元数据或恢复结果核实实际 cwd。恢复需要调用方指定 cwd 时，先核实这个值。
3. **执行身份**：提交、观察和停止都能区分本次执行和后继执行。机制不限，可以是原生执行 ID、请求与应答的配对，或宿主串行化加上原生协议的归属规则，但必须写明。
4. **接受判定**：每次写入得到三种结果之一：
   - **已接受**：能归属到这条输入的正证；
   - **明确未投递**；
   - **效果未知**。

   正证可以晚到，最晚与终态同时到达，在此之前状态为“未定”。只有正证才按捕获版本推进群聊游标；明确未投递、未定和未知都不推进。未定期间保留准确目标，拒绝会覆盖该目标的新输入，停止仍然可以执行。
5. **终态与结果**：每个由输入启动的执行，都有能归属到它的终态（完成、中断、失败），以及该执行的结果正文或明确的“无正文”、失败原因。正文只按原生身份或原生协议的归属规则归属。运行中追加的输入各有自己的接受判定，与原执行共用一个终态和投递锚点。
6. **重检**：观测丢失时，能按原执行身份做有界核验，结果是仍在运行、已有终态或仍未知。核验可以始终得到“仍未知”。此时按既有规则保留原身份和占用，只隔离这个 Binding，不释放，也不重放。
7. **停止**：停止落地时只作用于目标执行。原生停止请求不带执行身份时，必须由原生协议或宿主保证在停止生效之前后继执行不可能开始，例如 Netizen 作为该会话唯一的写入方，在停止期间保持这个 Binding 的准入关闭。只有会话 ID、发送前核验或提示，都不足以满足本条。原生停止会附带停止的后台工作必须写明，并在停止入口说明。
8. **观察源**：本后端接管的每条原生观察源只有一条宿主消费链，其他模块复用这条链的投影。后端把原生事件翻译成共用展示事件，不把原生类型交给共用层。
9. **发行物与停服**：启动时验证已验收的原生发行物（版本或指纹）和所需能力。停服时在宿主预算内尝试关闭本实例的原生连接，逾期如实记录，未确认关闭的连接或执行按既有规则隔离。

运行中追加输入（steer）不属于核心，是一个能力模块。未声明该模块的后端，在忙时于写入前拒绝新输入，提示稍后重发，不排队。

ADR 0105 第 5 条的四项不变量（版本比较、接受后推进游标、停止前比较身份、停服预留预算）由 Netizen 实现一次，对每个后端都生效。后端只提供上述事实，不需要提供 Codex 专有的证明条件。

### 3. 能力模块与模块卡片

每个模块有一张卡片，字段固定：

| 字段 | 内容 |
| --- | --- |
| 标识与名称 | 稳定的模块标识 |
| Netizen 语义 | 用户和管理员看到什么、Netizen 保证什么，不提任何一家 Agent |
| 端口 | 宿主调用的最小操作和后端产生的事件，用 Netizen 的术语写 |
| 能力项 | 可以单独启用的部分，例如目录的“指定会话摘要”和“归档分页” |
| 原生事实 | 兑现语义所需的契约层事实，与某个后端的实现机制分开 |
| 入口与资格 | 哪些操作、输入形态、观察或结果处理、MCP 工具使用哪个能力项；关联零到多个操作描述条目 |
| 失败与降级 | 唯一的降级路径、影响范围和提示 |
| 展示事件 | 使用共用词汇表中的哪些事件 |
| 验收 | 与后端无关的契约断言，以及每个后端自己的原生门禁 |
| 依赖 | 依赖的其他模块；不同模块和能力项互不授予资格 |
| 实现状态 | 各后端是否实现，经由端口还是仍直连运行时 |

模块卡片在三种情况下补全：模块首次有第二个实现，首次由新后端提出，或者边界被修改。在此之前，模块表中的一行就是它的当前定义。

### 4. 扩展流程

1. **提出**：任何后端的原生能力，按[保留原生能力](../design.md#目标与边界)和飞书场景的收益权衡后，都可以提出为新模块、新能力项，或对已有模块的扩展。
2. **定义**：写出模块卡片。语义和端口用 Netizen 的术语，不照搬发起方 SDK 的类型或调用顺序；必须写明降级路径和验收方式。以下情况写 ADR：新增端口、新增展示事件、改变共用边界。只在已有端口和事件内增加行为时，直接更新工程设计中的模块表和卡片。
3. **注册**：登记模块标识、提供方和能力项。可以复用现有操作描述表，不另建注册服务。每个使用该模块的操作、输入形态、观察或结果处理、MCP 工具，在实际执行处按所需能力项核验。已有入口保持统一的资格判定，并核对原生探针和目标当前状态，手输命令、旧卡回调、Admin API 和定时派发都不例外。
4. **实现**：首个实现模块的后端定义、注册并验证它，其余后端保持关闭。之后采纳的后端（包括 Codex）直接实现同一端口，运行同一套契约断言和本后端的原生门禁，通过后开放。验收要覆盖能力项的组合，例如不支持 steer、支持图片但不支持 steer、只读协作，以及是否支持结果静默。因所需能力项未开放而在入口拒绝时，断言没有发出该操作的原生写请求。已经提交后才收到的原生拒绝，按该操作的契约记录未投递的输入或已完成的步骤。
5. **修订与移除**：模块语义变化时修订卡片，不在共用层按后端区分行为。一个模块不再有任何实现时，从代码中移除；需要时按本流程重新提出。

### 5. 结构规则

1. **共用逻辑只依据端口和能力项。** 共用的执行、资格判定和投递逻辑不按后端身份分支，不开平行路径。允许 setup 和启动时持久化或校验固定的后端身份，允许从已装配的提供方透传显示名称和既有协议中的身份字段。现有直连 Codex 运行时的调用是第 6 条的迁移点，不因本条立即关闭。
2. **展示事件词汇表封闭。** 共用展示只消费 TurnOpened、ActivityChanged、PartialAnswer、RunState、TurnResult、RunEnded 和 DeliveryReceipt，投递策略只有一种。新增事件或投递模式需要 ADR，并且要有至少一个真实后端的生产者和真实的消费者。
3. **保证只建立在原生公开报告的事实上。** 这些事实由门禁固定。实测时序和等待时长不能作为证明。缺少事实时，关闭对应能力项，或走它的降级路径。
4. **通用门禁绑定其实际触发事实。** 打包、回执、准入屏障等通用检查，不能挂在某个后端专属的键或标志上。
5. **契约断言与后端无关。** 核心和每个模块各有一组契约断言。每个后端通过生产适配器和实际宿主入口运行它声明的全部部分，用本后端的夹具控制原生输入和输出，另外运行模块的原生门禁。

### 6. 演进方式

- Codex 是参考实现，实现了核心契约和多数模块，但很多调用仍直连 `CodexRuntime`。不做一次性重构。
- Codex 目前有一个已知差距：原生已开始执行、提交回执尚未返回的短窗口内，停止入口会报告没有执行，不能停止目标。补齐后才能认定 Codex 满足全部核心契约。验收顺序固定为：原生建立执行，扣住回执，发出停止，核对目标与结果，再放行回执。用回执到达之后的停止测试代替无效。
- 第二个后端要实现某个已有模块时，如果已有实现仍直连运行时，先冻结该实现的行为，把对应调用移到端口后面，再接入新实现。冻结的做法是：改动前记录已有实现的解码输出，改动后逐项比较。
- 由其他后端首创的模块，首个实现直接经端口接入，Codex 日后采纳时直接实现同一端口。
- 接入第二个后端之前，必须先整理核心边界：
  - Channel 和管理装配只依赖核心端口；
  - 宿主不变量与 Codex 的证明条件分开；
  - 状态提供方与后端无关；
  - 展示接线由提供方翻译原生事件。

### 7. 暂不纳入

原生输出无法归属到任何已接受的输入时（例如后台工作结束后自行唤醒的回复），本 ADR 不规定其处理方式，也不把它算作下一条人工输入的结果。实际接入的后端需要时，按扩展流程以新模块定义。

## 备选方案

| 方案 | 取舍理由 |
| --- | --- |
| 一个覆盖所有能力的大接口 | 后端要为缺失能力提供空方法，调用方容易把占位结果当作有效数据。ADR 0105 已否决。 |
| 以 ACP 等现成协议作为 Netizen 的后端契约 | 协议只是某个后端的传输方式。Codex 不走该协议，Netizen 的 Scope、Binding 和飞书投递语义也不在协议范围内。模块定义可以参考协议，但不以它为准。 |
| 只写原则，不写模块表和卡片 | 原则无法在复审中逐项核对，试点就是在缺少成文条目的情况下逐项发现缺口。 |
| 按操作描述整项开关模块 | 一个操作常常同时使用核心、宿主和多个模块的能力。整项关闭会连带关闭核心功能，例如本地会话列表和宿主的会话设置。 |
| 先抽取完整的执行内核，再接入新后端 | 只有一个实现时抽取的内核会带着这个实现的形状。按模块在真实的第二个实现出现时再移到端口后面。 |
| 把无法归属的原生输出纳入核心 | 目前没有实际接入的后端可以验证规则，按维护者裁定暂缓。 |

## 后果

- 新后端的评估从核心契约的原生事实清单开始。事实不满足时，在写代码之前就能判断它不能接入，或者只能接入到哪一层。
- 新能力可以由任何后端首先提出，再由 Codex 等其他后端按同一模块实现。
- 复审有了可以逐项核对的门槛。以下情况都属于阻断问题：新增的后端分支、共用展示中的新投递模式、依赖时序的证明、挂在后端专属键上的通用检查。
- 接入第二个后端前，需要先完成第 6 条列出的核心边界整理。这部分工作随具体后端的接入决定一起排期。
