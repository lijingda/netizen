# 原生已实现的语义交给原生决定，Antigravity 待 ACP v2 后再接入

## 背景

[ADR 0111](0111-define-an-extensible-backend-contract.md) 定义了后端契约。维护者随后按这份契约评估 Google Antigravity 作为下一个后端，调研记录保存在本地研究目录 `docs/research/antigravity/`。评估分三步：官方资料与无认证握手；两种接入面的源码比较；用维护者自己的登录，分别在 1.5.12 和 1.5.18 上实测 `agy acp`。

两种程序接口：

- `agy acp`：用户本机的 `agy` 以子进程方式提供 ACP（Agent Client Protocol）JSON-RPC 服务。协议组织发布了官方 Python 客户端库 `agent-client-protocol`，许可证为 Apache-2.0，类型由官方 schema 生成，可以精确固定版本。
- Python SDK `google-antigravity`：启动随包附带的运行时。公开接口和文档没有保证它与用户已有的 CLI 或 ACP 会话能按同一 ID 互相续接，本次也没有实测互开。它不报告实际 cwd，每条输入没有可配对的标识，停止请求不带执行标识，忙时发送会等待上一轮结束。

`agy` 1.5.18 在握手时只协商 ACP v1：客户端请求版本 2 或 3 时，它都返回 1。实测中对后端契约有用的 v1 事实如下：

- 第一条输入之前就有会话 ID，能列出会话，能跨进程按 ID 续接（1.5.12 与 1.5.18）。
- 续接时即使传入别的目录，会话仍在原 cwd 中执行，会话列表也报告原 cwd（1.5.12 与 1.5.18）。
- 两个版本成功返回的 `session/prompt` 应答都带 `stopReason`。
- 1.5.12 上两次实验都是在第一条请求还没返回、工具也还没启动时发出第二条。两次都看到第一条请求很快返回，后续工作由第二条承接。
- 1.5.18 上，显式的非 daemon 样本在应答之前完成；显式的 daemon 样本在应答之后才出现工具完成事件和唤醒正文。工具事件带 `toolCallId`，正文既没有请求 ID，也没有消息 ID。
- 运行中的取消由目标请求的 `cancelled` 应答确认，取消通知本身没有回执（1.5.12 与 1.5.18）。
- 进程被强制结束后，原请求的终态无法找回（1.5.18）。
- 1.5.12 上还观察到：成功编辑带 diff；一次 stdio MCP 调用的 `_meta` 带有 `agy` 附加的会话 ID。

按 v1 接入，以下几项缺少原生事实：

- **执行身份**：v1 允许省略 `messageId`，这两个版本的 `agy` 在所测样本中都没有提供。输出片段只带会话 ID，无法可靠归属到某条请求；阶段性答案需要的逐条消息身份也没有。
- **接受证明**：要等到终态才知道输入被接受，期间群聊游标无法推进。
- **停止**：会话级取消没有回执，不能证明它不会作用于后继请求。
- **后台工作**：没有原生的空闲与后台工作状态，宿主无法判断何时可以安全关闭连接。

ACP 官方文档的 v2 预览提供了以下内容：

- 用户消息插入会话后即应答，应答带 `messageId`；消息更新都带各自的 `messageId`。
- `state_update` 报告前台状态，可以附带后台工作快照。`background` 缺省或为 null 表示未知，显式的空清单才表示没有后台工作。
- `session/cancel` 取消当前的前台工作，以及此前已收到但尚未插入的 prompt。之后收到的 prompt 不会被这次取消作用，但新的前台工作要等取消完成后才开始。已列出的后台工作继续运行，未列出的后台活动可能被停止。
- 客户端可以给 prompt 提供幂等键，重复识别只在原生仍保留该键的范围内有效。
- 协议明确建模了 agent 自主发起的工作。

这些内容并不直接证明“哪段输出、哪个终态属于哪条输入”。协议也允许原生暂存忙时收到的 prompt，稍后再插入。所以 v2 是否满足后端契约，要按定稿的协议和 `agy` 的原生证据重新验收。目前 `agy` 不协商 v2，官方 Python 库也把 v2 放在实验命名空间里。

## 决定

### 1. 原生已实现的语义交给原生决定（修订 ADR 0111）

这是一条适用于所有后端的通用规则：

1. **先核验宿主状态。** 所有者门禁、能力项、Scope 与 Binding 身份、捕获版本、群聊游标，以及停止、生命周期和未知占用这些宿主状态，在写入前先核验。任何一项不满足，就在写入前拒绝。
2. **再委托原生语义。** 宿主状态全部有效后，忙时如何处理、配置值是否合法、权限策略、会话状态是否允许某个操作，都交给原生。Netizen 直接发出请求，按原生应答映射结果，不重复判断。
3. **判断标准。** 原生的应答能证明发生了什么，就委托。委托会产生无法归属或无法撤销的效果时，宿主才前置拒绝。例如 Codex 的压缩应答不带轮次标识，压缩期间宿主拒绝新输入。

Codex 现有的前置检查不单独排查，在 ADR 0111 第 6 条的核心边界整理中按这条规则逐项对照。

### 2. 忙时输入的两种方式（修订 ADR 0111 第 2 条）

核心契约允许两种忙时处理方式，都不由 Netizen 排队：

- **宿主在写入前拒绝**：适用于原生不能对忙时请求逐条给出明确应答的后端。
- **由原生逐条应答**：原生对每条请求都直接给出接受、拒绝或接续的应答。这时宿主不做忙时前置判断。原生只是排队等待上一轮结束后才处理的，不算这种方式。

运行中追加输入有两种模型。每条输入都有自己的接受判定，ADR 0111 第 2 条“与原执行共用一个终态和投递锚点”的表述只适用于并入模型：

- **并入**：后一条输入并入正在执行的那一轮，共用原执行的终态和投递锚点。Codex 属于这种，对应“运行中追加”模块。并入模型和要求精确物理轮次的入口，仍须携带可以核验的执行身份。
- **接续**：每条输入都是对这个精确会话的一次独立请求，各自确认终态，结果投递到各自的原请求位置，后一条可以接手前一条的工作。宿主在提交前观察到会话换代时，旧的捕获失效；提交之后的原生竞态可以让这次请求成为一次新的执行。

在 Codex 上，人工消息、问题卡片回答和定时输入保持精确轮次准入。采用接续模型的后端，普通输入以捕获的会话和准入版本为目标；要求精确物理轮次的入口仍须携带该身份。

### 3. Antigravity 暂缓接入

- **方向**：将来通过 `agy acp` 和精确固定版本的官方 ACP 客户端库接入，驱动用户自己的 `agy` 运行时。不采用 Python SDK。
- **不在 ACP v1 上接入。** 在 v1 上补齐上述缺口，需要按请求时间窗口归属输出、停止竞争时回收连接、在群聊补齐上下文时前置拒绝、自定连接保活策略等宿主变通，还会让本轮文件和阶段性答案无法开放。
- **重新评估的条件**，同时满足以下三项时，用 v2 的实测事实另写接入 ADR，并逐项确认哪些 v1 变通已经可以移除：
  - ACP v2 定稿；
  - `agy` 协商 v2；
  - 官方 Python 库的 v2 不再处于实验状态，可以精确固定。
- 维护者已确定的接入前提保留到届时：
  - 实例只供所有者本人使用；
  - 启动时及每个新的 `agy` 进程首次使用前，都核验已验收的版本和所需能力；
  - 首期范围为核心普通会话，加上会话目录、Activity、模型设置和图片输入。

  本轮文件和阶段性答案到时按 v2 的消息与工具标识另行判断。

### 4. 核心边界整理随下一个后端一起进行

ADR 0111 第 6 条的核心边界整理，按原定安排在接入下一个后端时进行：先冻结 Codex 的行为，再把对应调用移到端口后面。届时同时按本 ADR 第 1 条对照 Codex 现有的前置检查。有真实的第二个实现作依据，端口的形状不会只照着 Codex 来定。

## 备选方案

| 方案 | 取舍理由 |
| --- | --- |
| 现在就在 ACP v1 上接入 Antigravity | 需要一组只为 v1 存在的宿主变通，输出可能误归属，本轮文件和阶段性答案无法开放；v2 可用后还要逐项重新评估这些变通。 |
| 通过 `google-antigravity` SDK 接入 | SDK 启动随包附带的运行时；它与用户已有的 CLI 或 ACP 会话按同一 ID 互开没有公开保证，另外缺少实际 cwd、逐输入标识和带执行目标的停止。 |
| 宿主对所有后端统一在忙时前置拒绝 | 原生能逐条应答时，宿主再判断一次既重复原生语义，也丢掉原生的接续能力。 |
| 解析工具参数（例如是否以 daemon 方式运行）判断会话状态 | 这些参数属于具体工具，不在协议之内。 |
| 不等第二个后端，现在就整理核心边界 | 只有 Codex 一个实现时抽出的端口会带着 Codex 的形状；ADR 0111 已规定随第二个后端的接入一起排期。 |

## 后果

- 委托原生语义成为通用的设计原则，AGENTS.md 和贡献指南各加一条。工程设计的后端契约补上忙时处理的两种方式和两种运行中追加模型，AGENTS.md 的精确轮次准入规则限定到 Codex 与要求精确轮次的入口。
- 当前契约中的后端仍只有 Codex。Antigravity 的调研结论和 v1 实测记录保存在研究目录，供满足条件后重新评估。
