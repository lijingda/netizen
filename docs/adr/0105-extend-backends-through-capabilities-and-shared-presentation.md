# 按能力接口与共用展示扩展多后端，并规划 Claude 原生能力

## 背景

[ADR 0104](0104-host-native-agent-backends-per-instance.md) 的普通会话试点已能让飞书和 Claude Code CLI 按同一会话 ID 顺序续聊。试点也留下了一个用户可见的缺口：首答发出后，断开客户端可能终止尚在运行的后台任务，用户收不到 Claude 原生唤醒后给出的完成轮回答。

在 `main@d36c781`，按 Channel、管理、Admin 和 Worktree 四处统计，约有 78 处按后端分支的判断，另有启动装配分支。Channel 和回复呈现器的 `_runtime` 访问器仍返回 `CodexRuntime`，管理层的生命周期与历史操作也依赖 Codex。`BackendPolicy` 用操作名字符串白名单为 Claude 筛选入口。`/status`、`/sessions` 和表单已有两套展示路径，Claude 实例的 Admin 删除确认却仍警告将删除 Codex 历史。单独开放手工改名就会遇到这个问题：放行通用的 rename 名称会同时放行生成名称，而管理层仍只会调用 Codex。两个后端还分别编排了 Binding 锁、准入版本、回执、精确停止与关闭，其中游标写入失败的处理已经分歧。

固定的 `claude-agent-sdk==0.2.186`（随附 CLI 2.1.329）已公开 `rename_session`、`fork_session`、`delete_session`、`get_session_messages`。客户端有 `stop_task`、`set_model`、`get_context_usage` 和 `get_mcp_status`。选项支持 `effort`、`thinking`、`include_partial_messages`、`skills`、`plugins`。进程内 MCP 可用 `create_sdk_mcp_server`，原生提问可经 `can_use_tool` 回调。这些 API 给出了可以验证的操作，飞书入口还需分别证明目标、结果与权限语义。

维护者要求保留原生能力，优先采用公开 SDK。逐项衡量飞书中的收益、终端交互依赖及命令冲突，例如截图起聊需要可靠续接，终端的 `@` 补全则无需搬入聊天。定时计划、输入准备和结果投递等 Netizen 功能在各后端遵循同一套产品规则。

以上事实与取舍依据本地研究目录 `docs/research/multi-agent-positioning/phase4-design/` 中的 `MERGED-REVIEW.md`（维护者裁定）、`ARCH-REVIEW-LEAD.md` 与 `ARCH-REVIEW-CODEX.md`（源码位置、固定 SDK 与夹具证据）。

## 决定

1. **在装配处穷举后端工厂。** ServiceCore 按实例已选后端静态选择工厂。工厂装配普通会话端口、停服端口及该后端已验证的能力。历史实例缺省仍选 Codex，显式后端无法装配则启动失败。每实例一个 Runtime，每个原生会话由 Netizen 单写入，每条原生事件流只有一个消费者。新增后端须显式修改装配代码。
2. **按实际调用方引入小接口。** 保留 `OrdinarySessionPort`。当手工改名、历史读取等操作有了真实调用方，为它接入实际存在的提供方，并绑定该后端的契约夹具与原生验收门禁。Codex 可以包装现有 Runtime 方法。缺少提供方或证据时关闭该操作，调用方无需实现占位方法。
3. **每项操作由同一份描述驱动。** 每个操作 ID 对应具体语义、提供方、资格和入口，供帮助、菜单、表单字段、Admin 以及服务端分发共用，取代字符串白名单。手工改名和生成名称各有自己的 ID。执行时，手输命令、旧卡回调、Admin API 与定时派发都须重新核对提供方、目标身份、版本、所有者资格及资源当前状态。显示过按钮不能授权执行。
4. **后端填充共用展示模型。** 状态、会话列表、表单、Result 和 Admin 复用字段定义。每个字段标明来源，观测值还标明采样时刻。例如，Binding 登记时间取自 Netizen，实际 cwd 取自原生会话元数据，用量取自对应执行的观测。区分“不适用”（该后端没有此概念）、“未观测”（本次尚无样本）、“取不到”（应有数据但读取失败）。例如 Claude 状态中的 Codex Goal 属于不适用，未收到用量时不能填零。原始工具参数、输出与推理仍由后端过滤。
5. **在已有锁和执行路径中只提取四项不变量。**
   - 复用同一把 Binding 锁，捕获输入后在提交前比较版本。准备期间即使从 A 切到 B 又切回 A，旧捕获也失效。
   - 各后端给出本次输入被接受的原生证明后才推进群聊游标。共用比较并交换（CAS）屏障；持久化失败即关闭实例后续执行准入，继续跟踪和投递这次已接受的执行。
   - 停止前比较 Binding、版本和执行身份，旧按钮不能击中后继执行。实际 interrupt 及终态仍由后端确认。
   - ServiceCore 经 `SessionShutdownPort` 给出同一停服截止时间，各后端在剩余预算内关闭自己的资源并报告未确认项。Codex 的 steer、Goal 换轮、订阅和 App Server 关闭顺序，以及 Claude 的接受证明、隔离和客户端关闭顺序，均留在各自后端。

### Claude 路线与维护者裁定

**D1．按 A → B → C → D → E 推进。** C 可以与 B 的界面迁移并行。每阶段对 Codex 均须保持行为等价。

| 阶段 | 交付与边界 |
| --- | --- |
| A 修复试点缺陷 | 修正 Claude 已接受输入后群聊游标 CAS 失败仍允许新输入的问题。省略 `system_prompt` 会让固定 SDK 传空的 `--system-prompt`，改用公开预设 `{"type":"preset","preset":"claude_code"}`，不追加宿主指令。按实际后端与操作清单修正 Admin 删除确认、重启时的 Codex／Goal／Side 文案、诊断目录和“继承 Codex”。扩充两个后端的普通端口参数化测试，覆盖 CAS 失败、捕获后切换、回执取消、过期停止、迟到关闭和两个 Binding 在同一 cwd 并行。 |
| B 迁移入口与展示 | 引入静态工厂、小接口、操作描述与共用模型。先迁移 `/status`、`/sessions`、表单和 Admin 文案，用手工改名走通一个已有提供方的真实操作。Claude 手工改名的开放仍在 D 验收。 |
| C 投递后台完成轮 | 将客户端寿命与单次人工输入分开，每个活动 Binding 只消费一条接收流。首答及时投递，后续由原生通知唤醒的完成轮回到发起任务的飞书锚点。验收条件见下节。 |
| D 按证据开放能力 | 依次交付 ① Activity 和有本轮 Write 证据的 Files，② 只读历史，③ 手工改名和精确持久 fork，④ 一个原生 AskUserQuestion 作答流程，⑤ 定时任务，⑥ 协作读取。每项分别验收，问题和定时的边界见 D6。 |
| E 验证第三个后端 | 先完成 Phase 0 Track C，验证 Antigravity 的 `agy acp` 能证明普通会话身份、恢复与停止，再经同一套契约接入。 |

**D2．同一 Binding 有后台交接待完成时拒绝输入。** 在提交给 SDK 前向所有者显示“首答已发，后台任务仍在运行”。输入不排队，其他 Binding 可照常执行。待 SDK 能证明人工请求与原生唤醒各自的归属后，再评估运行中合并。

**D3．首条为图片时，先验证创建时命名。** 对新会话通过 `extra_args` 传 CLI `--name`，仅在创建时设置可见短名。已有内存探针能读回标题，但记录开头缺 cwd 时得到 `cwd=None`。须用原生首图夹具证明按精确会话 ID 能稳定恢复实际 cwd，才采用该做法。证明不足时继续拒绝续接，不猜 Project 默认目录或覆盖历史标题。

**D4．权限仍只覆盖为会话级 `auto`。** 状态可只读展示有来源的模型、effort 与用量。开放模型选择和 effort 选择各需后续明确批准。

**D5．先手工改名和精确持久 fork，再决定删除语义。** 修订 ADR 0104 决定 7 对 Claude 缺少原生删除的前提：固定 SDK 已有 `delete_session`。开放前须定义外部写入者仍活动或重新写入时的处置、失败与结果未知的边界、subagent 数据清理和 Project 级联，并在可丢弃的原生会话上验证。此前继续在预览拦截含已物化 Claude 会话的 Project 删除。Claude 归档保持关闭。

**D6．原生 cron、问题和协作写入分别决策。** cron 唤醒只按原生事件处理；Netizen Plan 的认领和派发仍归唯一 Scheduler。AskUserQuestion 的回答须绑定所有者、原卡、客户端代际和工具调用，由正在等待的回调接收；该路径单独验收，不扩大其他工具权限。协作读取的验收只覆盖读取，协作写入另行裁定来源身份、目标和准入。

## 验收与门禁

每个实施阶段都需通过 `make check`、Codex 与 Claude 两个原生回归组（`make check-native` 和 `make check-native-claude`）、Claude 原生组中经飞书消息与卡片入口的 Channel E2E，以及 Admin 浏览器 smoke（`make check-browser`）。核对 Codex 的输入准入、原生执行与界面操作结果和迁移前一致。改变原生行为时另跑受影响的 live smoke，Claude 使用 `scripts/check_native_claude.py --live`。平台回归与真实账号结果分别记录。[仓库验收说明](../deployment.md#代码门禁与按需实时兼容性验证)

C 的合入以后台任务发起人能收到正确的回答、且不会中断后继执行为准：

- 首答投递后保持所需客户端与唯一接收流，由 Claude 原生唤醒，无需 Netizen 再发 `query()`。按客户端代际、发起输入 UUID、原飞书锚点及可观测的任务／工具调用关联归属。在内存中对同一原生结果去重；只有可归属的 Result 产生完成轮正文。仅收到终态 `TaskUpdated` 只能证明任务状态。
- 覆盖双任务乱序、任务先于首答结束、Result 混入人工 UUID、重连时的事件重放、cron 或未知来源，以及飞书投递失败。可确认的完成轮只向原锚点投递一次；归属不足则报告未知，不选最近一次发言。验证待交接时的同 Binding 忙拒及同 cwd 其他 Binding 并发。
- 关闭须有任务及完成轮均已交接、可释放客户端的正向证据，事件流暂时安静不能证明空闲。仅在能证明仍是同一执行时允许精确停止。用迟到停止卡、换轮、停服及重启验证，不会中断后继执行。分别验证连接释放、CLI 回收和外部 CLI 顺序续接，并复核原有启动宽限与停服总预算。

## 备选方案

| 方案 | 取舍理由 |
| --- | --- |
| 提取完整会话内核 | 两端在接受证明、释放活动槽、终态和关闭顺序上不同。统一状态机会把 Codex 的证明条件带给其他后端，四项局部不变量已能解决实际分歧。 |
| 只维护字符串白名单 | 一个名字无法说明是否有实现、手工与自动改名的语义差异，以及目标当前能否执行。界面和分发仍会各自维护判断。 |
| 定义一个覆盖所有后端的大接口 | 实现方要为 Goal、Side 等缺失能力提供空方法，调用方容易把占位结果当作有效数据。 |
| 运行时发现并注册后端插件 | 后端已在 setup 固定，每种 SDK 都要精确锁定并独立验收。动态发现增加未验证的装配组合。 |
| 立即采用 Claude 的运行中输入合并 | 原生 Result 可能同时带后台通知和人工输入 UUID，目前无法可靠区分发起锚点和可停止的执行。按 D2 暂缓。 |

## 后果

新增能力时，调用方与后端须明确操作、证据和失败边界，再复用飞书与 Admin 的展示。不同后端可以分期开放同一操作。Claude 的写入与提问仍受所有者门禁约束，后台交接只延长有原生工作待完成的客户端寿命，不引入输入队列、第二个 Scheduler 或本地会话历史。本草案记录拟议修订，当前运行契约仍见 [ADR 0104](0104-host-native-agent-backends-per-instance.md) 和[工程设计](../design.md)。
