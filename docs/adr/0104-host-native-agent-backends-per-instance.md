# 按实例接入多个原生 Agent 后端

## 背景

Netizen 目前把飞书接成 Codex 的 Channel：守则和契约都以一个共享 `AsyncCodex` 为前提。
维护者决定让 Netizen 接入更多完整的 Agent 运行框架，例如 Claude Code 和 Google Antigravity。
这里接入的是各家的原生 harness，而不只是让 Codex 调用其他厂商的模型。

各家 Agent 的原生能力不同，例如：

- 运行中追加输入能否精确并入当前轮；
- 是否有 Goal、临时分支、持久 fork、归档和删除；
- 是否支持原生提问；
- 能否分页读取历史；
- MCP 工具调用能否带上可信的调用方身份。

在 Netizen 现有 Runtime 中，自有不变量和 Codex 的证明条件写在同一组方法里。前者包括
Binding 锁、准入版本、未知态、停服预算；后者包括 Goal 换轮、Skill 订阅和 exact steer。
例如 `runtime/submission.py` 的提交主路径同时处理这两类条件。上层直接依赖具体的
`CodexRuntime`：仅统计 Channel、管理、定时、Admin、会话和卡片几层的直接调用，就至少有
119 个调用点、71 个方法名。另有四条旁路直接使用 Codex 的类型或错误：输入构造、协作读取、
Admin 错误识别和 Files 提取。错误文案（`error_messages`）、阶段性答案、账号额度等值类型
也带着 Codex 的形状，接入第二个后端时需要一并处理。

本决定先经过两路互不可见的独立架构审查，再合并裁定。

## 决定

1. **定位**
   - Netizen 是飞书上的 Agent Channel，每个实例（root）选择一个原生 Agent 后端。
   - Codex 是参考后端，保留现有全部能力与门禁。
   - 后端在实例初始化时选定，产生会话后不可更改；没有后端标识的历史实例固定解释为 Codex。
   - 后端身份和认证模式记在实例目录现有的配置里，不新增数据库字段。新程序在每次启动时校验它们。
     - 不认识这一项的旧版本程序会把实例当作 Codex 打开，所以 Claude 实例不支持用旧版本程序启动，用户手册写明。
     - 选择这种简单做法的代价是：误用旧版本时只会靠失败来暴露（例如恢复会话时找不到对应线程），而不是被提前拒绝。
   - 本 ADR 不支持同一实例内按会话混用后端、跨后端协作或迁移已有会话；需要时另立 ADR。
2. **接受能力差异**
   - Netizen 不用 Prompt、本地状态或私有接口模拟某个后端缺失的原生能力。
   - 后端缺失的能力不展示入口。所有入口在服务端用同一套资格判定拒绝，不调用该后端不支持的运行时操作，包括手动输入的飞书斜杠命令（如 `/goal`、`/side`）、卡片回调（含旧卡片）、Admin API 和定时派发。
   - 可选能力是带保证的操作，必须写明不可执行时的处置：明确拒绝、结果未知或展示不可用。每项能力按后端分别验证后才开放。
3. **执行所有权归后端**
   - 每个后端独占自己的 SDK 连接与进程模型、活动执行和唯一事件消费者。
   - 后端负责把原生事件翻译成 Activity、阶段性答案、Result 和 Files 的安全展示数据。
   - 以下部分各后端共用：飞书 Channel、输入准备、Project 与 Worktree、Admin、部署，以及四类回复卡片。
   - 同一原生会话能否同时被其他客户端（例如原生 CLI）写入，由该 Agent 自身的策略决定。Netizen 只保证自己对每个会话是单一写入者，不增加跨客户端写锁、占用检测或冲突修复；各后端的原生行为写入用户手册。
   - **服务重启后的短暂重叠（接受的风险）。** Netizen 在 macOS 上崩溃后，launchd 约 0.2–1.2 秒就会重启服务，而上一代 Claude CLI 约 2 秒后才退出；Linux 的 systemd 会等旧进程退干净再重启。如果新进程在这段时间里恢复同一个会话，两个进程可能同时写会话记录，之后再恢复时，最近一轮可能不在 Agent 的上下文里。
     - 本 ADR 接受这一风险，理由有三：
       - 只有崩溃和同一会话的新消息同时落在约 2 秒的窗口内才会发生，概率极低；
       - 后果只是 Agent 可能忘掉最近一轮，用户重新提问即可，记录文件不会损坏；
       - 这与"其他客户端能否同时写入由 Agent 自身策略决定"的决定一致。
     - Codex 后端维持现状：App Server 是 `AsyncCodex` 的子进程，由 Codex 管理其退出。
     - **简单缓解。** Claude 后端在服务每次启动后约 2 秒才开放 Claude 会话准入。这期间收到的 Claude 消息会明确回复"服务刚启动，请稍后重发"，不排队。
       - 这个时长按实测的退出时间设定，测试版本为 claude-agent-sdk 0.2.186、随附 CLI 2.1.329。它只降低概率，不是保证；SDK 或随附 CLI 升级时要复核。
     - **崩溃后不再有模型请求。** 这依赖受管服务结束与 Netizen 同组的 CLI：macOS 上按进程组，Linux 上按 cgroup。两个平台都已实测：CLI 与 Netizen 在同一进程组，崩溃后没有新的模型请求。不经受管服务、以前台方式运行的调试进程不提供这一保证。
     - **备用方案。** 以后真出现问题，可以改用已经验证过的"代际锁"：CLI 继承一把锁的共享持有，新进程取得排他锁后才开放准入。实验证据已存档。
     - **范围。** 以上只针对会写会话、会调用模型的 Agent CLI 本身。工具启动并已脱离的后台进程（例如开发服务器）不由 Netizen 回收，与 Codex 后端一致：Netizen 本来就不扫描、也不向 Agent 的工具进程发送信号。Linux 上这类进程会随服务的 cgroup 一起结束；macOS 上可能在 Netizen 崩溃后继续运行，这一差异写入用户手册。
4. **接口按普通会话逐步建立**
   - 先沿普通会话的完整路径建立窄接口：捕获准入、创建或精确恢复、提交一次、观察这次执行的结论、停止同一次执行、有界关闭。
   - Codex 的现有实现原样放在接口后面。
   - 共同不变量先写成共享契约测试；第二个后端稳定后，再抽取两处相同的编排代码。
5. **新后端首发只提供普通会话，运行中拒绝新输入**
   - 运行中收到的新输入，在调用 SDK 前明确拒绝。只有证明"不排队、不跨轮"的精确语义后，才对该后端开放 steer。
   - "未提交"的拒绝文案只用于本地确实没有调用 SDK 的情形；调用后失去回执时，报告提交结果未知。
6. **审批仍是非目标**
   - 新后端使用其原生的非交互权限策略；需要真人批准、又没有可验证应答通道的操作，按原生策略拒绝。
   - 飞书没有逐步确认的交互通道，逐步审批卡会让聊天充斥确认卡片，所以两个后端都不使用交互式审批，只是做法不同：
     - Codex 后端省略审批参数，从而采用公开 API 的默认值 `auto_review`，不继承用户在交互式使用中的审批设置。
     - Claude SDK 的默认模式在无人值守时会拒绝写入和命令，所以 Netizen 通过 SDK 公开选项，为每个 Claude 会话显式传入原生 `auto` 权限模式，由 Agent 自带的审核机制自动判断每个操作。这是对原生默认值的显式覆盖，本 ADR 接受时作为新的原生配置例外写入 AGENTS.md。该模式只作用于本会话，不写入用户设置。
   - 用户在 Claude Code 设置中的 deny 与 ask 规则仍然优先。Netizen 不添加允许规则，也不提供 `bypassPermissions` 等跳过检查的模式。
   - `auto` 不可用时（例如模型不支持，或管理员关闭了该模式），原生表现可能是退回默认模式，也可能是会话启动时报错，须实测确认。无论哪种，Netizen 都不改用更宽松的模式：
     - 退回默认模式时，未预先允许的操作一律被拒绝，Netizen 向用户说明原因；
     - 启动时报错发生在提交输入之前，按"未发送输入"报告。
   - Netizen 将来注册的专用工具需要的权限，另行决定。
   - Agent 的阻塞式提问回调与 Codex 问题卡"以普通输入作答"是不同的授权路径，单独设计后才开放。
7. **生命周期操作按后端开放**
   - archive、delete、restore 和 fork 只对经验证提供对应原生操作的后端开放。
   - 没有原生删除的后端不提供删除入口，不以删除本地登记冒充原生删除。
   - 对没有原生删除的后端，删除 Project 时，含已物化会话的 Project 在预览阶段就被拦截。Codex 后端继续使用 ADR 0060 的精确清单删除。
8. **认证**：每个后端只使用厂商允许第三方产品采用的认证方式。
   - **Netizen 不接触 Agent 账号凭据。** 不实现任何 Claude 登录流程；不读取、保存或转发 Claude 凭据与会话令牌；不修改 Claude Code 程序，也不禁用它自带的认证方式。
   - **提交前核对认证来源。** 每个会话在 SDK 连接建立后、提交任何输入前，读取 SDK 公开方法 `get_server_info()` 返回的握手信息，核对实际认证来源。
     - 提交输入之后才出现的初始化信息不能用于准入。
     - Netizen 不读取凭据的值，也不以"环境变量是否存在"代替这项核对。
     - 握手信息中的账号字段目前没有正式文档，所以按批准的窄适配处理：精确锁定 SDK 版本，有独立的 synthetic 与 live 门禁；字段缺失、形状变化或组合无法识别时，一律关闭连接、拒绝执行。
     - SDK 提供有文档的认证来源接口后，迁移过去并删除这个适配。
   - **Claude 后端的认证模式在 setup 时按实例选定**，之后只能在主机上更改：
     - **API key 模式（默认）**：使用 Anthropic API key 或厂商支持的云平台凭据，费用计入凭据所有者，可供多人使用。不得回退到主机上的订阅登录：握手显示的来源不是所配置的 API key 或云平台凭据时，拒绝执行。
     - **所有者专用订阅模式**：订阅所有者本人在主机上，通过官方 Claude Code 登录流程登录；Netizen 只运行未修改的官方程序，由程序自行读取凭据。
       - 提交输入前，同样核对握手信息：必须显示为第一方订阅，且没有选中 API key；否则拒绝执行。
       - **登记所有者。** 沿用 setup 现有的首位管理员流程（ADR 0062、0080）：在 setup 中通过飞书网页授权的用户，或用 `--admin-open-id` 指定的用户，就是订阅所有者，不另加主机确认。飞书授权本身已经确认了是用户自己在操作；验证链接被转发的风险与现有首位管理员相同，沿用现有处理。
       - **所有者门禁。**
         - Admin 一侧：订阅模式下，管理员名单只有所有者一人。Admin 隐藏"添加管理员"，服务端也拒绝添加。Admin 只有所有者能登录，所以 Admin 的其他功能都不用改动。
         - 飞书一侧：会触发执行的消息和操作（普通消息、问题回答、定时计划的创建与维护）只接受所有者本人。其他人的消息（含群聊中 @ 机器人）在调用 SDK 前拒绝。
         - 定时任务照常开放：只有所有者能创建和维护计划。Agent 在所有者的会话中通过定时工具为自己设置的唤醒（例如几小时后回来检查状态），同样视为所有者本人的操作。
       - **保存与更改。** 所有者就是实例管理员名单里的那位用户，沿用现有的 `state/admin-users.json`，不另存一份。
   - **未取样的认证来源保持关闭。** 某种认证来源（例如有效 API key、Bedrock、Vertex）的握手字段组合，在取得实际样本之前不被识别为合格，对应模式不可选。认证本身由 Agent 完成，Netizen 只需确认自己能正确识别它。
   - **身份对应由部署者负责。** Netizen 无法、也不尝试核实飞书身份与 Claude 账号属于同一人；这一对应由部署者在 setup 时声明，合规责任由部署者承担。用户手册默认推荐 API key 模式。
   - **依据**：[Anthropic 法律与合规](https://code.claude.com/docs/en/legal-and-compliance)规定，开发者不得在自己的应用中提供 Claude.ai 登录，不得代其用户经订阅凭据转发请求，也不得收集、保存或中转 Claude 凭据，登录须经 Anthropic 自己的流程完成。同一节又写明："Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code"。[消费者条款](https://www.anthropic.com/legal/consumer-terms)第 2 节规定，不得把账号提供给他人使用。
   - **尚未解决的歧义**：[Agent SDK 文档](https://code.claude.com/docs/en/agent-sdk/overview)写的是"Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products"，措辞与法律页的例外存在张力；消费者条款第 3 节对自动化访问也有限制。本 ADR 仍然开放订阅模式下的定时任务，理由有两点：一是计划只能由所有者本人或其会话中的 Agent 设置，属于所有者自己的使用；二是 Claude Code 本身也提供让 Agent 定时唤醒自己的能力。合规责任仍由部署者承担，必要时按法律页的指引向 Anthropic 询问。
9. **试点与传输**
   - 首个试点是经官方 `claude-agent-sdk` 接入 Claude Code。
   - Antigravity 优先评估官方 `agy acp`；ACP 可以作为单个后端的传输，不作为所有后端的产品契约。
   - Codex 继续使用官方 `openai-codex` SDK。
10. **依赖与门禁**
    - 每个后端各自精确锁定 SDK 和随附二进制，并有独立的无账号契约夹具、实机验收与升级审查。
    - 新增后端不能让现有的 Codex 安装失效，也不能让服务在运行时自行安装依赖。
    - Claude 的 SDK 或随附 CLI 每次升级，都要重新验证三件事：崩溃后 CLI 的退出时间（用来复核启动后的等待时长）、握手信息中的认证字段、`auto` 模式的行为。

## 接受条件

以下条件全部满足后，本 ADR 转为 accepted，并在同一改动中修订 AGENTS.md、design.md 和被修订的 ADR。

首个试点后端须用官方入口完成实测：

- 原生会话能与该 Agent 的原生 CLI 互相续接；
- 会话身份的获得时机以及 resume 失败的行为已经明确；
- 运行中拒绝新输入、停止目标的竞态在 Netizen 自身范围内可控；
- 各类结束状态可以区分；
- Netizen 异常退出后，不再产生新的模型请求，并且上一代 CLI 的退出时间落在启动后的等待时长之内。Linux systemd 与 macOS LaunchAgent 均需实测；macOS 还须在真实用户 Mac 上复验，覆盖开启 SIP、按登录项启动、注销与重启；
- 同一实际目录下并发会话的资源占用，以及 60 秒停服预算，均可满足；
- 服务账号下的非交互认证符合第 8 条，且能加载原生配置；
- API key 模式下，凭据缺失或无效时不会回退到主机上的订阅登录；
- 订阅模式下，飞书中非所有者触发执行的请求在调用 SDK 前被拒绝；Admin 无法添加管理员；
- 按会话指定的 `auto` 模式不写入用户设置；用户的 deny 与 ask 规则在该模式下仍然生效；Netizen 能在提交前确认实际生效的权限模式，或在不符时可靠地提示用户；
- `auto` 不可用时的原生表现（退回默认模式，或启动时报错）已实测，并按第 6 条处理；
- 服务启动后约 2 秒内的 Claude 消息被明确拒绝，之后自动开放准入；

## 备选方案

- **按能力注册工厂，组合出通用执行引擎**：steer、观察、关闭各自的前提在同一状态机里混搭后难以表达，组合与负面测试最多，回退时难以只撤一个动作。
- **一开始就定义覆盖全部功能的后端接口，或先从 Runtime 抽共享内核**：只有一个实现时，抽出来的接口是 Codex 的形状，会把 Codex 的证明条件一并搬走。
- **所有后端统一走 ACP（Codex 也经适配）**：Codex 会失去 exact steer、Goal、临时分支、生命周期操作和 Files 证据。ACP v2 草案把运行中 prompt 的处理交给 Agent 自行决定。
- **每个 Agent 做成独立产品，只共享小型库**：部署、Admin、定时和飞书交互重复建设，规则逐渐漂移。
- **进程外的通用执行网关或任务队列**：会新增常驻服务、任务身份和失败域，违反单服务边界。
- **权限完全交给用户在 Claude Code 设置中配置**：默认模式下，无人值守时写入和命令都会被拒绝；为了 Netizen 去放宽用户的全局设置，又会改变用户在终端里的使用方式。
- **逐步审批卡**：每个需要确认的操作都发一张卡片，聊天会充斥确认卡片，体验差；审批交互仍是非目标。
- **同一实例内按会话选择后端**：需要重做原生 ID 唯一性、MCP 来源、目录游标和设置快照；在有明确需求前不做。

## 后果

- 不同机器人提供不同的能力集，用户手册按后端说明可用功能。
- 本 ADR 接受时，AGENTS.md 中以下条款移入 Codex 后端专节，或改为按能力适用：
  - "Feishu/Lark Channel for Codex"
  - "one shared AsyncCodex"
  - 运行中输入 exact steer
  - 每个物化会话都保留归档与删除
  - Codex 控制原生配置
  - 标准 `CODEX_HOME` 与 Skill 根注册
- 以下条款作为跨后端约束保留：
  - 原生执行归 Agent
  - 同一目录可并发
  - 群聊准入
  - 附件所有权
  - 展示过滤
  - SQLite 数据白名单（不因本 ADR 新增条目）
  - 无队列、无第二份历史
- 被修订 ADR 的收窄范围：
  - ADR 0008：决定 1（使用一个 `AsyncCodex`）、决定 4（运行中输入映射为 steer）和决定 8（审批采用公开默认值）收窄为 Codex 后端内部的规则。
  - ADR 0074 与 0076：实例配置中增加后端身份和认证模式，并在启动时校验。
  - ADR 0060、0062、0068、0078、0080、0092：按上文对应条目收窄或补充。
  - 已被取代的 ADR 0002、0003、0007 不重新启用。
- 订阅模式在飞书可用范围、群成员资格以及 ADR 0092 的群聊开关之外，新增一条按认证模式生效的执行限制：只有所有者本人能触发执行或修改将要执行的内容。
  - 订阅模式下管理员只有所有者一人，Admin 权限不需要区分。AGENTS.md 中"实例管理员拥有平等 Admin 权限"的规则保持不变，只补充一句：订阅模式下不能添加管理员。
  - 不引入多角色权限体系。
- 维护成本大致按"后端数量 × 各自开放的能力"增长。跨后端协作会引入有向组合，因此推迟。
