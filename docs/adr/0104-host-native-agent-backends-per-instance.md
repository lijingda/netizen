# 按实例接入多个原生 Agent 后端

## 背景

作出本决定前，Netizen 把飞书接成 Codex 的 Channel，守则和契约都以一个共享 `AsyncCodex` 为前提。
维护者决定让 Netizen 接入更多完整的 Agent 运行框架，例如 Claude Code 和 Google Antigravity。
这里接入的是各家的原生 harness，而不只是让 Codex 调用其他厂商的模型。

各家 Agent 的原生能力不同，例如：

- 运行中追加输入能否精确并入当前轮；
- 是否有 Goal、临时分支、持久 fork、归档和删除；
- 是否支持原生提问；
- 能否分页读取历史；
- MCP 工具调用能否带上可信的调用方身份。

在 Netizen 现有 Runtime 中，自有不变量和 Codex 的证明条件写在同一组方法里。前者包括
Binding 锁、准入版本、未知态、停服预算；后者包括 Goal 换轮、Skill 订阅和 exact steer。
例如 `runtime/submission.py` 的提交主路径同时处理这两类条件。上层直接依赖具体的
`CodexRuntime`：仅统计 Channel、管理、定时、Admin、会话和卡片几层的直接调用，就至少有
119 个调用点、71 个方法名。另有四条旁路直接使用 Codex 的类型或错误：输入构造、协作读取、
Admin 错误识别和 Files 提取。错误文案（`error_messages`）、阶段性答案、账号额度等值类型
也带着 Codex 的形状，接入第二个后端时需要一并处理。

本决定先经过两路互不可见的独立架构审查，再合并裁定。

## 决定

1. **定位**
   - Netizen 是飞书上的 Agent Channel，每个实例（root）选择一个原生 Agent 后端。
   - Codex 是参考后端，保留现有全部能力与门禁。
   - 后端在实例初始化时选定，产生会话后不可更改；没有后端标识的历史实例固定解释为 Codex。
   - 后端身份记在实例目录现有的配置里，不新增数据库字段。新程序在每次启动时校验它。
     - 不认识这一项的旧版本程序会把实例当作 Codex 打开，所以 Claude 实例不支持用旧版本程序启动，用户手册写明。
     - 选择这种简单做法的代价是：误用旧版本时只会靠失败来暴露（例如恢复会话时找不到对应线程），而不是被提前拒绝。
   - 本 ADR 不支持同一实例内按会话混用后端、跨后端协作或迁移已有会话；需要时另立 ADR。
2. **保留原生能力，接受后端差异**
   - Netizen 不为简化接入而关闭或缩减 Agent 的原生能力。用户可以在自己的原生设置中关闭功能。只有飞书场景有明确收益才按会话覆盖原生策略，当前例外是第 6 条的 Claude `auto` 权限。
   - 是否接入一项原生能力，还要结合飞书的实际交互环境权衡：Agent 是否原生具备、在飞书中是否有实际价值（不依赖终端特有的交互）、是否与 Netizen 自身功能冲突。依赖终端交互的能力不必在飞书中重现，例如 Claude Code 带补全的 `@` 文件引用和原生斜杠命令（后者还与 Netizen 的飞书斜杠命令冲突，因此 Claude 会话按原样提交飞书文本）。不接入的能力记录原因。
   - Netizen 不用 Prompt、本地状态或私有接口模拟某个后端缺失的原生能力。
   - 后端缺失的能力不展示入口。所有入口在服务端用同一套资格判定拒绝，不调用该后端不支持的运行时操作，包括手动输入的飞书斜杠命令（如 `/goal`、`/side`）、卡片回调（含旧卡片）、Admin API 和定时派发。
   - 可选能力是带保证的操作，必须写明不可执行时的处置：明确拒绝、结果未知或展示不可用。每项能力按后端分别验证后才开放。
3. **执行所有权归后端**
   - 每个后端独占自己的 SDK 连接与进程模型、活动执行和唯一事件消费者。
   - 后端负责把原生事件翻译成 Activity、阶段性答案、Result 和 Files 的安全展示数据。
   - Claude Code 可以先结束当前回复，待后台任务完成时由原生通知唤起新一轮。下一阶段必须把这些完成轮的结果送回飞书。
   - 以下部分各后端共用：飞书 Channel、输入准备、Project 与 Worktree、Admin、部署，以及四类回复卡片。
   - 同一原生会话能否同时被其他客户端（例如原生 CLI）写入，由该 Agent 自身的策略决定。Netizen 只保证自己对每个会话是单一写入者，不增加跨客户端写锁、占用检测或冲突修复；各后端的原生行为写入用户手册。
   - **服务重启后的短暂重叠（接受的风险）。** 在 macOS runner 上，launchd 约 0.2–1.2 秒就重启宿主，上一代 Claude CLI 约 2.1 秒才退出；Linux systemd 实测先回收旧 CLI 再重启。只有新一代开放准入后又恢复了同一会话，尚存活的旧 CLI 才可能与它并发写入。此时原生恢复的上下文可能缺少最近一轮，用户需重新提问。
     - Codex 后端维持现状：App Server 是 `AsyncCodex` 的子进程，由 Codex 管理其退出。
     - **启动准入。** 新宿主先等飞书 Channel 就绪（实际启动约需 8 秒），再等 2 秒才开放 Claude 执行准入。过早收到的任务明确回复“服务刚启动，请稍后重发”，不排队。
       - 这个时长按实测的退出时间设定，测试版本为 claude-agent-sdk 0.2.186、随附 CLI 2.1.329。它只降低概率，不是保证；SDK 或随附 CLI 升级时要复核。
     - **崩溃后的模型请求。** Linux systemd 按 cgroup 回收，macOS launchd 管理宿主进程组。Linux 受管服务实测与 GitHub macOS runner 的 LaunchAgent 试验在观测窗内均无新模型请求。前台调试进程没有受管回收保证。所有者 Mac 的复验条件见下文。
     - **备用方案。** 以后真出现问题，可以改用已经验证过的"代际锁"：CLI 继承一把锁的共享持有，新进程取得排他锁后才开放准入。实验证据已存档。
     - **范围。** 以上只针对会写会话、会调用模型的 Agent CLI 本身。工具启动并已脱离的后台进程（例如开发服务器）不由 Netizen 回收，与 Codex 后端一致：Netizen 本来就不扫描、也不向 Agent 的工具进程发送信号。Linux 上这类进程会随服务的 cgroup 一起结束；macOS 上可能在 Netizen 崩溃后继续运行，这一差异写入用户手册。
4. **接口按普通会话逐步建立**
   - 先沿普通会话的完整路径建立窄接口：捕获准入、创建或精确恢复、提交一次、观察这次执行的结论、停止同一次执行、有界关闭。
   - Codex 的现有实现原样放在接口后面。
   - 共同不变量先写成共享契约测试；第二个后端稳定后，再抽取两处相同的编排代码。
5. **新后端首发只提供普通会话，运行中拒绝新输入**
   - 运行中收到的新输入，在调用 SDK 前明确拒绝。只有证明"不排队、不跨轮"的精确语义后，才对该后端开放 steer。
   - 只有能确认未向 SDK 提交输入时才回复“未发送”。写入后失去回执且无法核实结果时，报告提交结果未知，不自动重发。
   - Claude 的 Result 归属本次输入后，飞书立即准备回复，按实际工作目录上传正文引用的本地图片，与原生客户端关闭并行。收尾中的会话继续拒绝新输入，状态卡不再提供停止按钮。确认客户端关闭且投递尝试结束后才接受下一条输入。
   - 续接须从公开 SDK 的会话摘要确认原 ID 和实际工作目录。首条消息带大图时，可能已有记录但没有摘要，此时提示所有者检查原会话或用 `/new` 新建。
   - Claude 试点每次执行创建一个客户端，回复结束即关闭，仍在运行的原生后台任务随之停止。这是暂时的投递缺口。Netizen 不得通过设置 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` 取消第 3 条的后续轮次。
6. **审批仍是非目标**
   - 新后端使用其原生的非交互权限策略；需要真人批准、又没有可验证应答通道的操作，按原生策略拒绝。
   - 飞书没有逐步确认的交互通道，逐步审批卡会让聊天充斥确认卡片，所以两个后端都不使用交互式审批，只是做法不同：
     - Codex 后端省略审批参数，从而采用公开 API 的默认值 `auto_review`，不继承用户在交互式使用中的审批设置。
     - Claude SDK 的默认模式在无人值守时会拒绝未经允许的写入和命令。Netizen 通过 SDK 公开选项为每个 Claude 会话申请原生 `auto`，由 Agent 审核操作。该覆盖只作用于本会话，不写入用户设置。
   - 用户在 Claude Code 设置中的 deny 与 ask 规则仍然优先。Netizen 不添加允许规则，也不提供 `bypassPermissions` 等跳过检查的模式。
   - 随附 CLI 2.1.329 即使被项目设置禁用自动审核，init 仍可能报告 `permissionMode: "auto"`，实际操作仍被拒绝。init 不能证明单项操作已获准。
   - 本轮可归属的 `ResultMessage.permission_denials` 非空时，向所有者报告被拒次数，只列白名单中的工具名，省略参数、路径和自定义名称。init 报告 `default` 时提示使用默认权限；两种证据同时出现时，在结果前合并提示一次。
   - 启动在提交前报错，按“未发送输入”报告。提交后发现 init 缺少权限模式或模式不受支持，请求中断并报告结果未知，不放宽权限。
   - Netizen 将来注册的专用工具需要的权限，另行决定。
   - Agent 的阻塞式提问回调与 Codex 问题卡"以普通输入作答"是不同的授权路径，单独设计后才开放。
7. **生命周期操作按后端开放**
   - archive、delete、restore 和 fork 只对经验证提供对应原生操作的后端开放。
   - 没有原生删除的后端不提供删除入口，不以删除本地登记冒充原生删除。
   - 对没有原生删除的后端，删除 Project 时，含已物化会话的 Project 在预览阶段就被拦截。Codex 后端继续使用 ADR 0060 的精确清单删除。
8. **认证**：每个后端只使用厂商允许第三方产品采用的认证方式。
   - **Netizen 不接触 Agent 账号凭据。** 不实现任何 Claude 登录流程；不读取、保存或转发 Claude 凭据与会话令牌；不修改 Claude Code 程序，也不禁用它自带的认证方式。
   - **Claude 后端只提供所有者专用模式。** 一个 Claude 实例只供部署它的人本人使用。
     - Claude Code 在主机上如何认证，由所有者按官方方式自行配置：可以是所有者本人的订阅登录，也可以是所有者自己的 API key 或厂商支持的云平台凭据。无论哪种，都是所有者本人在使用，都在下文依据允许的范围内。
     - 因此 Netizen 不感知认证方式：setup 不选认证模式，Netizen 不读取也不核对认证来源，不需要相应的 SDK 窄适配，也不需要对各种认证来源取样。
     - **登记所有者。** 沿用 setup 现有的首位管理员流程（ADR 0062、0080）：在 setup 中通过飞书网页授权的用户，或用 `--admin-open-id` 指定的用户，就是所有者，不另加主机确认。飞书授权本身已经确认了是用户自己在操作；验证链接被转发的风险与现有首位管理员相同，沿用现有处理。
     - **所有者门禁。**
       - Admin 一侧：Claude 实例的管理员名单只有所有者一人。Admin 隐藏"添加管理员"，服务端也拒绝添加。Admin 只有所有者能登录，所以 Admin 的其他功能都不用改动。
       - 飞书一侧：会触发执行的消息和操作（普通消息、问题回答、定时计划的创建与维护）只接受所有者本人。其他人的消息（含群聊中 @ 机器人）在调用 SDK 前拒绝。
       - 所有者规则也适用于将来的定时入口。普通会话试点尚未开放定时任务；开放后，只有所有者能创建和维护计划，Agent 在所有者会话中为自己设置的定时唤醒也归属于该所有者。
     - **保存与更改。** 所有者就是实例管理员名单里的那位用户，沿用现有的 `state/admin-users.json`，不另存一份。
   - **身份对应由部署者负责。** Netizen 无法、也不尝试核实飞书身份与主机上的 Claude 认证同属所有者本人；这一对应由部署者在 setup 时声明，合规责任由部署者承担。
   - **暂不提供多人共用模式。** 多人共用的前提是 Claude Code 确实使用 API key 或云平台凭据，而 Netizen 在不感知认证方式的情况下无法保证这一点。服务通常运行在所有者自己的系统账号下，这个账号往往也登录着所有者的订阅；API key 没有进入服务环境时，Claude Code 会改用已登录的订阅而不报错，所有人的请求就都经过所有者的订阅。有明确需求时另行决定，可选做法包括由部署者声明，或核对 SDK 握手信息中的认证来源（相关账号字段没有正式文档，每种来源都要先取样，并作为窄适配管理）。
   - **依据**：[Anthropic 法律与合规](https://code.claude.com/docs/en/legal-and-compliance)规定，开发者不得在自己的应用中提供 Claude.ai 登录，不得代其用户经订阅凭据转发请求，也不得收集、保存或中转 Claude 凭据，登录须经 Anthropic 自己的流程完成。同一节又写明："Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code"。[消费者条款](https://www.anthropic.com/legal/consumer-terms)第 2 节规定，不得把账号提供给他人使用。
   - **尚未解决的歧义**：[Agent SDK 文档](https://code.claude.com/docs/en/agent-sdk/overview)写的是"Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products"，措辞与法律页的例外存在张力；消费者条款第 3 节对自动化访问也有限制。本 ADR 允许后续为所有者接入定时任务，理由有两点：一是计划只能由所有者本人或其会话中的 Agent 设置，属于所有者自己的使用；二是 Claude Code 本身也提供让 Agent 定时唤醒自己的能力。合规责任仍由部署者承担，必要时按法律页的指引向 Anthropic 询问。
9. **试点与传输**
   - 首个试点是经官方 `claude-agent-sdk` 接入 Claude Code。
   - Antigravity 优先评估官方 `agy acp`；ACP 可以作为单个后端的传输，不作为所有后端的产品契约。
   - Codex 继续使用官方 `openai-codex` SDK。
10. **依赖与门禁**
    - 每个后端各自精确锁定 SDK 和随附二进制，并有独立的无账号契约夹具、实机验收与升级审查。
    - 新增后端不能让现有的 Codex 安装失效，也不能让服务在运行时自行安装依赖。
    - Claude 的 SDK 或随附 CLI 每次升级，都要重新验证两件事：崩溃后 CLI 的退出时间（用来复核启动后的等待时长）和 `auto` 模式的行为。

## 接受记录

2026-11-21，维护者接受所有者专用的普通会话试点。验收版本为 `claude-agent-sdk==0.2.186`、随附 CLI 2.1.329。PR #306 的 Linux 与 macOS 原生回归组均通过，包含经飞书消息和卡片入口执行的 Channel E2E。真实登录运行 `scripts/check_native_claude.py --live` 共 12 项，11 项通过，权限回退一项仅由 mock 覆盖。[双平台 CI 记录](https://github.com/lijingda/netizen/actions/runs/44903749598)

| --- | --- |

| 会话身份与恢复失败 | Phase 0 Track A 观察到首个请求可早于记录落盘。CI 原生组验证显式 UUID、实际 cwd 和精确恢复失败时不另建会话。 |

| Linux 受管服务崩溃 | systemd 实例实测，自服务主进程被杀起，工具约 0.1 秒退出，CLI 约 2.5 秒退出，新服务约 5.7 秒启动、18 秒就绪；观测窗内没有后续模型请求。 |
| macOS LaunchAgent | Phase 0 macOS runner 两次测得 Bash 在 44 ms 内退出、CLI 约 2.1 秒退出，launchd 均先重启宿主；观测窗内无新模型请求。真实 Mac 复验按下述风险处理。 |
| 所有者门禁 | Channel E2E 用第二个合成用户尝试私聊、群聊 @ 和卡片，模型请求为零，Store 无变化；单元测试与 Admin HTTP 测试覆盖服务端拒绝。第二名真人的复验按下述风险处理。 |

维护者明确接受两项尚无真人或真机复验的风险：

- **所有者 Mac。** 暂无合适的真实 Mac。依据 Phase 0 macOS runner 的进程回收与代际锁报告、macOS CI 原生组和 Channel E2E、崩溃助手的 macOS 分支单测，以及 Linux 受管服务实测，接受 launchd 重启可能与旧 CLI 短暂重叠。首次在真实 Mac 部署 Claude 时，所有者须开启 SIP，按清单执行崩溃助手，记录初次启动、注销再登录和重启再登录的判定。[Mac 验收清单](../deployment.md#在所有者的-mac-上验收崩溃重启)
- **飞书第二名用户。** 目前只有合成第二用户和服务端测试。首次在有多名成员的聊天中使用 Claude 实例时，用另一名真实飞书用户复验所有者门禁。

## 备选方案

- **按能力注册工厂，组合出通用执行引擎**：steer、观察、关闭各自的前提在同一状态机里混搭后难以表达，组合与负面测试最多，回退时难以只撤一个动作。
- **一开始就定义覆盖全部功能的后端接口，或先从 Runtime 抽共享内核**：只有一个实现时，抽出来的接口是 Codex 的形状，会把 Codex 的证明条件一并搬走。
- **所有后端统一走 ACP（Codex 也经适配）**：Codex 会失去 exact steer、Goal、临时分支、生命周期操作和 Files 证据。ACP v2 草案把运行中 prompt 的处理交给 Agent 自行决定。
- **每个 Agent 做成独立产品，只共享小型库**：部署、Admin、定时和飞书交互重复建设，规则逐渐漂移。
- **进程外的通用执行网关或任务队列**：会新增常驻服务、任务身份和失败域，违反单服务边界。
- **权限完全交给用户在 Claude Code 设置中配置**：默认模式下，无人值守时写入和命令都会被拒绝；为了 Netizen 去放宽用户的全局设置，又会改变用户在终端里的使用方式。
- **逐步审批卡**：每个需要确认的操作都发一张卡片，聊天会充斥确认卡片，体验差；审批交互仍是非目标。
- **在服务环境中关闭 Claude 后台任务**：会使所有会话失去原生完成轮。保留用户的原生设置，下一阶段补齐投递。
- **Claude 后端提供 API key 多人共用模式，并核对 SDK 握手信息中的认证来源**：相关账号字段没有正式文档，每种认证来源都要先取样，每次升级都要复验；Netizen 也因此必须感知 Claude Code 的认证方式。首个试点只面向所有者本人，暂不需要，有需求时另行决定。
- **同一实例内按会话选择后端**：需要重做原生 ID 唯一性、MCP 来源、目录游标和设置快照；在有明确需求前不做。

## 后果

- 不同机器人提供不同的能力集，用户手册按后端说明可用功能。
- Codex 保留单一共享 `AsyncCodex`、运行中 exact steer、物化会话的归档与删除、原生配置控制、标准 `CODEX_HOME` 与 Skill 根注册。
- 各后端共用原生执行归 Agent、同目录并发、群聊准入、附件所有权、展示过滤和现有 SQLite 数据白名单的约束。均不引入输入队列或第二份历史。
- 被修订 ADR 的收窄范围：
  - ADR 0008：决定 1（使用一个 `AsyncCodex`）、决定 4（运行中输入映射为 steer）和决定 8（审批采用公开默认值）收窄为 Codex 后端内部的规则。
  - ADR 0074 与 0076：实例配置中增加后端身份，并在启动时校验。
  - ADR 0060、0062、0068、0078、0080、0092：按上文对应条目收窄或补充。
  - 已被取代的 ADR 0002、0003、0007 不重新启用。
- pip／uv pip 更新仅在环境内的 Claude SDK 与当前已装 Netizen 发行包为 `[claude]` 声明的固定版本一致时保留 extra。版本冲突在停服前拒绝，uv tool 依工具安装记录确认 extra。
- Claude 实例在飞书可用范围、群成员资格以及 ADR 0092 的群聊开关之外，新增一条按后端生效的执行限制：只有所有者本人能触发执行或修改将要执行的内容。
  - Claude 实例的管理员只有所有者一人，Admin 权限不需要区分。AGENTS.md 中"实例管理员拥有平等 Admin 权限"的规则保持不变，只补充一句：Claude 实例不能添加管理员。
  - 不引入多角色权限体系。
- Claude 实例不能供团队共用。团队需要共用时，使用 Codex 实例，或等多人共用模式另行决定。
- 维护成本大致按"后端数量 × 各自开放的能力"增长。跨后端协作会引入有向组合，因此推迟。
