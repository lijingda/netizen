## 已达成的设计共识

### 1. 自主模式保持简单，只新增消费判断入口

- 自主模式是可选项，用户自行决定是否接受模型误判；现有 @、@ 配合 catch-up 和
  私聊的使用方式继续存在。
- 决策模型只判断符合自主候选范围的当前未 @ 新消息是否需要消费。显式 @ 和控制操作
  保持第 11 节的直接入口。判定消费后进入现有消息处理流程，该启动 Turn
  就启动 Turn，该 steer 就 steer；不另建执行流程、消息队列或任务调度器。
- 不在代码中另外堆叠“是否值得插话”“运行中采用另一套语义分类”等业务规则。
  判断质量主要通过决策模型的提示与判定上下文改善。
- 现有会话身份、输入准入、并发与执行语义继续复用。这不意味着模型判定能绕过现有
  Runtime 的实际接收条件。

### 2. 决策上下文只积累选中的消息和最终回复

每次判断输入为：

> 历史摘要 + 尚未压缩的已消费消息与最终回复 + 当前候选消息

- “历史”不是整个群的所有消息，而是此前决策模型选中并实际接收的消息及相应最终回复；
  自主模式期间显式 @ 且实际被接收的消息也进入上下文，见第 13 节。
- 当前候选消息参与本次判断；若判定不消费，不进入持久的判定记录，也不进入摘要。
- Netizen 自己维护这份判定上下文，记录选中的消息、最终回复及压缩后的摘要。
- 记录按实际发生顺序追加，不强制一问一答：多条运行中 steer 可能只对应一条最终回复。
- 采用跟随 Netizen 会话（Binding）保存的方向：新建会话从空开始，恢复旧会话时恢复
  该会话的判定上下文；不同会话的记录不混在一起。

### 3. Netizen 输出只保留实际最终回复

- 放入决策上下文的是最终回复正文。
- 排除过程信息、Activity 展示、Files 模块和 Netizen 自动追加的固定 @ 提醒。
- 模型在正文中主动发出的 @ 保留，不能通过删除所有 @ 文本实现过滤。
- 最终回复更新判定上下文，但不触发对自身回复的新一轮消费判断。
- 实现时可从既有最终结果正文与通知元数据的分离处取得内容，避免靠卡片整体文本猜测。

### 4. 自主模式不复用 catch-up 自动补齐被跳过的群聊

- Codex 接收被选中的当前消息，保留现有当前消息来源与显式引用能力。
- 不因为本次触发，就把此前被决策模型跳过的大量聊天重新自动送入 Codex。
- 决策上下文中的记录、摘要用于判定，本身不默认注入用户的 Codex Thread。
- Agent 需要理解指代、回顾或汇总时，自行按需读取当前飞书聊天／话题历史。
  这复用现有 `netizen-lark` 能力，而非新造历史查询接口。
- 在选中消息提交时，可附带两次消费之间未自动提交的用户消息条数，具体共识见第 5 节。
- 现有能力从当前 `message_id` 定位 `chat_id`／`thread_id`，依赖运行环境安装
  `lark-cli`、`lark-im`／`lark-shared` 等配套能力；Channel 存在本身不代表这些工具已安装。
- 按需查历史只能补齐已经触发的任务。如果决策模型直接漏判，Agent 没有机会再查历史。
  这是当前简化设计接受的局限，不以此重新引入 catch-up。决策提示应允许接收
  “值得处理，但需要执行者查上文”的请求。

### 5. 选中消息附带轻量的未消费条数提示

- 在决策模型确认消费后、提交现有执行流程时，为当前消息加一小段应用生成的上下文说明。
  例如：

  > 上一条已消费消息与当前消息之间，有 7 条用户消息未自动提交给你；如需上下文，可按需查询飞书历史。

- 没有这类消息（条数为 0）时不加提示。
- 条数只反映两条已消费消息之间、同一飞书会话范围内未自动提交的用户消息，不含两端消息，
  不混入其他聊天／话题；不计机器人回复、过程信息、Files 模块、固定提醒或表情事件。
- 不附带被跳过的消息正文、列表或内容摘要。这是上下文缺口的提示，不是 catch-up，
  也不是要求 Agent 必须查询历史；是否查、查多少仍由 Agent 按当前任务决定。
- 说明与用户原始正文分开，作为 Netizen 生成的元数据，不冒充用户发言；保持现有
  来源标记、显式引用、Turn 启动与 steer 行为。
- 实现保持轻量：利用消息接收过程维护必要计数／位置，不为计数保存被跳过的正文，
  也不在每次触发前额外拉取完整历史。准确计数不可得时，不编造精确条数。
- 具体计数状态与实际输入准入同步的时点等留待实现细化，不因此引入新的执行调度。

### 6. 压缩使用独立的纯文本摘要任务

- 不把当前 Codex `/compact` 当成“任意文本输入、返回通用文本摘要”的接口。
- 设计方向是复用现有共享 Codex SDK，创建内部临时会话，显式提交决策上下文待压缩的文本，
  取得纯文本摘要。可借鉴后台命名辅助任务的临时任务与资源收尾方式。
- 摘要任务只接收指定的决策记录，不为获取上下文而复制用户完整原生 Thread。
  摘要不作为用户任务回复发到飞书，也不改变用户当前 Thread 的上下文。
- 达到长度预算后，用“旧摘要 + 较早的一段记录”生成新摘要，保留最近一段原始记录。
- 新摘要成功保存后，再替换被压缩的旧段；不在每条群消息到达时都调用 Codex 摘要。
- 摘要重点保留参与者、主题、决定、已完成事项和待回应问题。
- 临时会话调用、摘要质量和清理方式仍需实现阶段验证，不能视为已有可直接调用的摘要组件。

### 7. 决策能力与具体模型解耦，首期支持 Jev 和 Laya

- 产品与核心业务采用“决策模型”“决策上下文”等中性术语；Jev、Laya 是可替换的供应方实现，
  不是自主模式本身的名称或执行流程的依赖。
- 核心只依赖一个小的异步接口：`decide(决策上下文, 当前消息) -> consume | skip`。
  调用失败与有效的 `skip` 分开表示；失败时的产品行为见第 12 节。
- Netizen 负责保存供应方无关的选中消息、最终回复和文本摘要；适配层负责模型请求／响应转换。
  现有 Turn／steer 流程不需要了解背后使用了哪个模型。
- 首期面向 Jev 服务和用户自行部署的 Laya HTTP 服务，可共享两者兼容部分的 System One
  请求／响应处理；以 `consume`／`skip` 两选项的 Choice 满足本场景即可。
- 接入通过配置和少量适配代码完成：协议／适配器、服务地址、模型、凭据引用、超时、输入预算。
  兼容协议的服务尽量只改配置；不兼容协议再增加薄适配器，不追求纯配置覆盖任意协议。
  具体配置字段与凭据保存方式尚未定稿。
- 输入预算是供应方差异的一部分。按选定模型的实际限制预留当前候选和判断问题的空间，
  再安排摘要与近期记录；不能依赖服务端静默截断。候选本身超长而无法判断时，按第 14 节处理。
- 切换供应方不改变持久记录含义或格式；必要时重新压缩以适应较小预算，不切换用户执行流程。
  不把不同模型的 confidence 当成可通用的阈值，也不承诺两者准确率或性能相同。
- 首期不做插件系统、通用分类工作流或模型服务生命周期管理；Netizen 只接入已提供的服务。
  “支持 Jev 和 Laya”是已确认的设计目标，不是已完成互操作和效果验证。

协议和限制的调研证据见 [Jev 与 Laya 供应方研究](decision-model-providers-2026-09-24.md)。

### 8. 决策模型只通过 Admin 配置，会话入口只选择模式

- 不实现自然语言修改决策模型配置，不新增配置 Skill 或 router Skill，也不新增决策模型
  维护 slash command 或 `/settings` 中的模型配置表单。
- `netizen-user-guide` 保持咨询职责：说明自主模式的行为、启用条件与使用方式；用户询问
  如何配置或修改决策模型时，引导实例管理员到 Admin 操作，不代改文件或读取凭据。
- Admin 维护实例级决策模型连接及凭据。配置好连接不自动为所有会话开启自主模式。
  沿用现有 Admin 身份认证，不把能发送飞书消息视为拥有管理员权限。
- `/new`、`/config` 只增加自主模式选项，不承载提供方、地址、API Key 等连接配置，
  不嵌入配置向导；会话参数继续沿用现有管理语义。
- 用户在 `/new` 选择自主模式并确认时，如果尚未配置决策模型，明确提示：

  > 决策模型尚未配置，请联系实例管理员在 Admin 中完成配置后，重新创建自主模式会话。

  此次不创建半可用会话，不自动改成其他模式，也不在配置完成后自动补建。
  `/config` 同理：缺少配置时拒绝切换，保留原有会话设置。
- 配置仍需持久保存以供重启恢复，但不把外部直接编辑文件作为首期产品配置流程。
  Admin 保存操作负责校验、持久化并更新运行中的决策配置，不做文件变更监听或轮询重载。
- “修改后直接生效”的边界是后续新判断使用新配置；已开始的判断保留其配置快照，
  不因此重启服务或打断已运行的 Codex Turn。不能仅落盘便宣称运行态已应用。
- Admin-only 收敛的是产品入口，不新增多用户文件隔离，也不能替代现有主机权限与
  Codex sandbox；具体存储、凭据保护和提交失败边界仍需实现时落实。

### 9. 安装零额外必答项，用到时再配置

- 决策模型是可选增量能力。不配置时，Netizen 的原有模式仍完整可用，不属于安装不完整。
- 默认安装流程不增加决策模型配置问答，连“是否跳过”也不要求用户选择。
  仅在安装完成信息中提示：配置决策模型后可以使用自主模式，不配置不影响现有使用。
- README 与 `netizen-user-guide` 增加自主模式说明和 Admin 配置入口指引。
  未配置却尝试启用时，按第 8 节在提交阶段提示用户去 Admin，不在会话卡片中补配置。
- 安装、升级和普通启动不以外部决策服务在线为前提；不默认下载模型、安装推理运行时
  或部署 Laya。服务可达性与判断失败的处理属于可选功能自身，不扩大为基础部署门禁。

### 10. 不消费时保持安静，数据去向仅作静态说明

- 有效的 `skip` 不发送“已忽略／不消费”等群通知，也不为这次跳过产生进度卡或处理提示。
  调用错误不是 `skip`；错误反馈遵循第 12 节，不逐条制造群聊噪音。
- “候选消息即使最终不消费，也先发送给决策服务判断”是数据流说明，不是逐条消息通知。
  可在 README、用户指南或 Admin 配置页静态写明；启用界面若放简短说明，也不需额外弹窗
  或每次请求确认。
- 说明应准确区分：候选消息参与当前判断；只有选中的消息及最终回复进入 Netizen 维护的
  决策上下文。Netizen 不保留跳过正文，不等于承诺外部提供方不会按其自身策略留存请求。
- 第 5 节的未消费条数提示只包装进后续被选中消息的 Codex 输入，不单独向群里发通知。

### 11. 自主模式取消“必须 @”，但保留显式触发与控制入口

- 符合自主候选范围的未 @ 消息交给决策模型判断；明确 @ Netizen 的普通消息直接进入
  现有消费流程，不经决策模型否决。用户可通过 @ 对漏判作显式补救。
- `/stop`、`/config` 等控制操作保持现有识别、作用范围和准入规则，不经过决策模型；
  不因为新增自主模式而扩大命令权限或改变既有操作语义。
- “直接进入”仍受现有消息准备与 Runtime 接收条件约束，不代表绕过失败或忙碌状态。
  自主模式中的显式 @ 也不自动带入被跳过的聊天，保持不复用 catch-up 的共识。

### 12. 判断不可用时不自动消费，显式入口继续可用

- 超时、密钥失效、管理员清除决策配置等导致无法判断时，未 @ 消息本次不自动消费，
  不积压、不在恢复后补跑，也不直接交给 Codex 兜底处理。
- 显式 @ 和控制操作不依赖决策服务，继续按原有条件可用。
- 不逐条向群聊发送判断失败通知；通过 Admin／`/status` 展示自主判断不可用及原因，
  不暴露密钥等敏感内容。错误展示与具体恢复状态的更新方式留给工程设计。
- 保留会话选择的自主模式，不因短暂故障或配置被清除而偷偷切换会话设置。
  服务恢复或重新配置后，只对新到的候选消息继续判断。
- 内部明确区分“模型有效判定为 skip”和“判断失败／不可用”，不能把故障伪装成模型选择。
  该状态不扩大为 Netizen 基础服务启动或安装门禁。

### 13. 模式切换不自动补录历史，已有决策上下文保留

- 新会话从空开始，恢复会话恢复该 Binding 的决策上下文；已有会话首次开启自主模式时，
  也从启用时刻开始积累，不自动导入此前群聊或原生 Thread 历史。
- 关闭自主模式后保留已有决策上下文，关闭期间不继续为自主判断额外收集消息或回复；
  再次开启时沿用已保留的记录，不补录关闭期间的交互。
- 自主模式期间，显式 @ 且实际被 Runtime 接收的普通消息及其最终回复，也进入决策上下文，
  避免决策模型不知道刚刚发生的显式交互。仍不混入控制消息、过程展示或固定提醒。
- 模型选中但未实际被 Runtime 接收的消息，不能记录成已消费交互；准入与记录提交的具体
  一致性处理留给实现阶段。
- 删除会话时一并删除该会话的决策上下文；不因仅关闭自主模式或切换模型提供方而删除它。

### 14. 首期自主候选限于真人群消息，判定投影不替代原始输入

- 首期自主候选为群聊主线／普通话题中的真人未 @ 消息。其他机器人不新增自主触发能力，
  已有明确 @ 行为保留；Netizen 自身最终回复只更新上下文，不触发自我判断。
- 图片、文件等非纯文本消息，先向决策模型提供可用文字和类型说明，不额外调用大模型
  做识图、文件解析或语义补全。首期接受这种判定信息有限所带来的误判。
- 判定消费后，原始消息仍按现有能力准备和提交；不能将决策模型看到的简化投影替代
  后续 Codex 输入，也不因此改变既有附件支持范围和失败语义。
- 当前消息本身超过决策模型窗口而无法完成判断时，按“判断不可用”处理，不静默截断后
  假装完成了完整判断；用户仍可通过显式 @ 走现有消费入口。
- 具体消息类型的文字／类型投影、token 预算计算等留给工程设计，不增设多级语义分类流程。

## 当前功能划分

1. 自主判断：通过可替换的决策模型对新消息作消费决定，必要时附带未消费条数提示，
   再接入现有消息处理。
2. 判定上下文维护：保存选中消息、最终回复、摘要，并按预算执行压缩。

暂不扩展为群聊全量存档、自动 catch-up、另一套执行调度或复杂的多级分类系统。
产品入口由 Admin 配置、会话模式选项及文档／安装提示承载，不新增自然语言配置体系。

## 尚待细化的实现事项

以下主要由工程设计按已确认原则收敛，不再把第 11—14 节已确定的产品选择作为未决项。

- Admin 接入配置的具体字段、持久化位置与凭据保护方式、模型版本，以及最终判断提示与协议映射细节。
- Admin／`/status` 的错误状态投影、恢复更新方式，以及保存失败和运行态应用失败的最小处理方式。
- 判定上下文的具体存储结构、模式切换与会话删除时的持久化一致性。
- “模型选中”和“Runtime 实际接受”之间的提交与记录一致性，以及准入失败的内部表示；
  不能把未被接收的消息记作已消费，也不能把被接收但尚未完成的消息记作已完成。
- 条数提示在首次启用、恢复／接收缺口、并发消息和准入失败时的最小处理方式；计数边界
  应与实际消费一致，不能把仅选中但未被 Runtime 接受的消息宣称为已消费。
- 摘要触发预算、保留多少近期原文、摘要任务使用的模型配置、压缩期间新记录的合并方式。
- 压缩失败时的最小处理方式，以及图片、卡片、转发等非纯文本输入的具体判定投影；
  遵守不额外调用大模型解析、无法判断时不自动消费的产品边界。

## 实施时需要同步的工程边界

当前工程对 Channel 保存消息正文、回复和历史有明确限制。本设计提出保存自主模式专用的
判定上下文，落地时需要明确修订对应契约与持久化范围；本备忘不将其冒充为现有能力，
也不以换存储文件位置规避该边界。普通 Codex Thread／Turn 历史仍由原生 Codex 拥有。
